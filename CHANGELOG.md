### Added — 2026-08-17 (app-cli: FLASHROM_INFO/READ/WRITE/DELETE and SYSINFO_INIT/SYSINFO_ID implemented for real)
- **Confirming the previous vbr-gate entry first**: confirmed against a real Sonic Adventure run — real interrupt delivery works mechanically (the fix compiles and behaves correctly), but the run revealed a separate, deeper issue: with `HleBootLoader.INITIAL_SR` in effect, the very first captured `LDC Rn,SR` write after boot (`PC=0x8C0101A2`) shows the game's own code **re-masking `SR.IMASK` back to `15`** (`SR 0x60000001 -> 0x600000F1`), and it never lowers `IMASK` again in any of the writes captured all the way through to the `BRA -2` idle loop. Since `SR.IMASK=15` is the maximum representable priority mask, **no maskable interrupt can ever be accepted while it holds** — meaning the `BRA -2` loop cannot be woken by `tryDeliverInterrupt` as currently modeled, regardless of how correct the delivery mechanism itself is.
- This reframes the loop: it's less likely a normal "wait for VBlank" idle wait (which would need interrupts unmasked to ever resolve) and more likely a deliberate halt/panic path the game enters after an earlier check fails in a way real hardware never would. `FLASHROM_READ` unconditionally returning failure was the most likely candidate this session identified: real, unconfigured Dreamcast consoles still have functioning (if blank) flashrom — reads *succeed*, just returning erased (`0xFF`) data — so a game checking system settings via `FLASHROM_READ` and getting an outright failure (this project's previous behavior) is a condition real hardware never actually produces, and the game's own error handling for "read failed" may differ significantly from its handling for "read succeeded, but the value looks unconfigured."
- Implemented `FLASHROM_INFO`/`FLASHROM_READ`/`FLASHROM_WRITE`/`FLASHROM_DELETE` for real, backed by an actual in-memory 128KB `flashRom` (`byte[]`) — not per-call fabrication. Initialized entirely to `0xFF`: real NOR flash's documented erased-cell value, confirmed against two independent sources that agree exactly — `mc.pp.se`'s own description of the erase operation, and redream's independent `flash.c` (`flash_erase` explicitly fills with `0xff`). This is the only state this project can honestly claim for a factory-fresh, never-configured console without a real dumped `flash.bin` — fabricating specific "realistic" region/language byte values without a confirmed source would itself have been exactly the kind of unlabeled guess this project's discipline avoids.
- Real partition table (5 partitions spanning `0x00000`-`0x1FFFF`, 128KB total) and per-function register conventions confirmed against `mc.pp.se/dc/syscalls.html`'s own worked example table and prose — one of this project's established primary references from the very first session: `FLASHROM_INFO` (`r4`=partition 0-4, `r5`=output pointer to two `int32`s: offset, size), `FLASHROM_READ`/`FLASHROM_WRITE` (`r4`=absolute flashrom offset, `r5`=guest buffer pointer, `r6`=byte count), `FLASHROM_DELETE` (`r4`=a partition's own start offset, not a partition number).
- `FLASHROM_WRITE` only ever clears bits (`flashRom[i] &= sourceByte`, never sets them) — the real physical constraint of NOR flash without a prior erase, confirmed against the same two sources. `FLASHROM_DELETE` erases the matched partition's real byte range back to `0xFF`, matching real hardware's documented erase behavior.
- `SYSINFO_INIT` now really copies real bytes — from `flashRom`'s partition 0 — to the documented fixed RAM address (`0x8C000068`-`0x8C00007F`, 24 bytes, confirmed against `mc.pp.se`), and `SYSINFO_ID` now returns a real, stable, non-null pointer to that address instead of the null pointer it used to return. Real hardware documents no failure case for `SYSINFO_ID` at all — a real caller would never guard against a null return, so the old behavior (returning `0`) was arguably a worse mismatch with real hardware than an outright failure code would have been. `SYSINFO_ICON` still honestly fails: `mc.pp.se`'s own page states the real icon data format is genuinely undocumented ("The format those icons are in is not known"), so fabricating one would be actively harmful, not just incomplete — a case where continuing to report failure is the correct, honest choice.
- 15 new JUnit tests in `BiosSyscallHandlerTest`, replacing the single `flashromAlwaysReportsFailureForEveryDocumentedFunction` test (which asserted the old, now-superseded blanket-failure behavior — a test that would now fail against the new code, not just needed a addition): `flashromInfoReturnsRealPartitionOffsetsAndSizes`, `flashromInfoFailsForAnInvalidPartition`, `flashromReadReturnsHonestlyBlankErasedBytesAndReportsSuccess`, `flashromReadFailsForAnOutOfRangeRequest`, `flashromWriteOnlyEverClearsBitsMatchingRealNorFlash`, `flashromWriteFailsForAnOutOfRangeRequest`, `flashromDeleteErasesTheWholePartitionBackToBlank`, `flashromDeleteFailsWhenTheOffsetIsNotAPartitionsOwnStart`, `sysinfoIdReturnsARealNonNullPointerAfterInit`.
- `BiosSyscallHandler`'s constructor now also seeds `flashRom` to all `0xFF` (`java.util.Arrays.fill`) — the one piece of real per-machine initialization this entry needed beyond the existing GDROM queue-state fields.
- **Not yet confirmed against a real `./gradlew` run or a real disc run past this point** — verified instead with a standalone `javac`-based manual harness in a sandbox with no Gradle/Maven Central access (15/15 checks passing, reusing the same `MemBus` test double already established for this class's existing GDROM tests).
- *AI usage: yes — implemented with Claude (Anthropic), including web research to confirm the real flashrom partition table, register conventions, and erase/write semantics against `mc.pp.se/dc/syscalls.html` and redream's independent `flash.c` before writing any code. This is a huge improvement over the previous stop (12,793,103+ steps to even reach a spin-wait) proving the mechanism itself is correct.

### Added — 2026-08-15 (core-system/core-cpu-sh4/app-cli: HleBootLoader.INITIAL_SR — real interrupt-mask fix for BIOS-free HLE boot)
- **Confirming the previous LDC Rn,SR-logging entry first**: confirmed against the real Gradle suite by the project owner — `Sh4CpuTest` 162/162 passing, `BUILD SUCCESSFUL` — and against a real Sonic Adventure run: all 16 real `LDC Rn,SR` writes captured across the entire observed boot sequence, and **not one of them ever changes `IMASK` away from `15`** — only `SR.BL` and `SR.T` ever change (e.g. `SR 0x700000F1 -> 0x600000F1` at `PC=0x8C649CAE`: `BL` clears, `IMASK` stays `1111`).
- Since `LDC Rn,SR` is the *only* real SH-4 instruction that can write `SR` at all, and a released, working commercial game unquestionably does receive real VBlank interrupts on actual hardware, this is direct, strong evidence Sonic Adventure's own code was never written to lower `IMASK` itself — it assumes the real BIOS (which this project's HLE boot entirely skips) already left it low enough by the time `1ST_READ.BIN` starts running. Exactly the same category of assumption already found and fixed for `PR`/`r[15]` (`HleBootLoader.BOOT_RETURN_SENTINEL`/`INITIAL_STACK_POINTER`) — this time for the interrupt-priority mask instead of the call-return/stack state.
- New `HleBootLoader.INITIAL_SR = 0x60000000`: `MD=1`/`RB=1` preserved from `Sh4Cpu`'s own real hardware reset value (the most plausible state a real BIOS would still leave the CPU in — this project has no behavior depending on these bits either way), `BL=0` (matching every observed real `LDC Rn,SR` write's own eventual state — the game's own critical-section pattern only makes sense if it expects interrupts through once it clears `BL` itself), `IMASK=0000` (fully unmasked — the simplest value consistent with "the BIOS already finished its own interrupt-priority setup," and with real code never touching `IMASK` anywhere in the observed trace). `T=0` (unaffected either way — real code sets it explicitly via comparisons before relying on it).
- **Honestly flagged as inferred from strong direct evidence, not a pinpoint-cited real BIOS memory dump** — unlike `BOOT_FILE_ENTRY_ADDRESS`'s or `INITIAL_STACK_POINTER`'s citations, no publicly available authoritative source documenting the real Dreamcast boot ROM's exact `SR` value at the `1ST_READ.BIN` handoff was found despite searching (KallistiOS's own `entry.s`/`irq_enable` was checked and doesn't apply directly — it clears `BL` and `IMASK` together via a single `AND`, but Sonic Adventure predates KallistiOS and uses Sega's own official SDK, which evidently follows a different convention that leaves `IMASK`'s adjustment to something other than a general `LDC Rn,SR`, or to the BIOS). This value is explicitly marked in its own Javadoc for revisiting if a more authoritative source is ever found — this project's discipline of "log gaps loudly, don't silently fabricate confidence" applied to a boot-time constant, not just an opcode.
- New `Sh4Cpu.setSr(int)`: the same real hardware-level whole-register overwrite `LDC Rn,SR` performs, exposed publicly so `Main` (the boot-loading caller) can apply `INITIAL_SR` the same direct way it already sets `pr`/`r[15]`. Kept as a method, not a public field (unlike `pr`/`r[15]`/`vbr`), specifically so `sr` stays encapsulated behind `tFlag()`/`blFlag()`/`imaskLevel()` rather than inviting a caller to desync those helpers' meaning from the raw bits by poking the field directly.
- `Main` now calls `cpu.setSr(HleBootLoader.INITIAL_SR)` right alongside the existing `cpu.pr`/`cpu.r[15]` boot-time initialization, with a comment explaining why, matching the established pattern exactly.
- 4 new JUnit tests: `initialSrUnblocksInterruptsAndFullyUnmasksThem`/`initialSrPreservesModeAndBankBitsFromTheRealResetValue` in `HleBootLoaderTest` (confirms the constant's own bit layout); `setSrOverwritesTheWholeRegisterMatchingLdcRnSr`/`setSrThenTryDeliverInterruptWorksEndToEndWithTheRealHleBootValue` in `Sh4CpuTest` (the latter confirms the actual real-world fix end to end: `tryDeliverInterrupt` blocked at `Sh4Cpu`'s own raw reset value, then delivered after `HleBootLoader.INITIAL_SR` is applied — the exact scenario this entry exists to fix). `Sh4CpuTest` 164 tests total; `HleBootLoaderTest` 8 tests total.
- **Not yet confirmed against a real `./gradlew` run, and not yet re-run against the real Sonic Adventure disc past this point** — verified instead with standalone `javac`-based manual harnesses in a sandbox with no Gradle/Maven Central access: 5/5 `HleBootLoader.INITIAL_SR` constant-property checks, 6/6 `Sh4Cpu.setSr`/end-to-end interrupt-delivery checks, plus a full regression re-run of 55 previous checks across every `core-cpu-sh4` entry this session (`OCBP`/`FMOV`-family/`MOVT`/interrupt-delivery), confirming no regression.
- **Confirmed against the real Gradle suite by the project owner: `Sh4CpuTest` 164/164, `HleBootLoaderTest` 8/8, `BUILD SUCCESSFUL`. Confirmed against a real Sonic Adventure run: a real interrupt genuinely fired** — `PC` correctly jumped to `vbr + 0x600` — the mechanism works. This uncovered a separate, real sequencing gap (`VBR` still `0` at that point) rather than the `BRA -2` loop itself — see the entry directly above for that fix.
- *AI usage: yes — implemented with Claude (Anthropic). This entry's core finding (that `IMASK` is never touched across 16 real `SR` writes) came directly from analyzing real execution data the project owner provided, not from web research — the earlier web research into KallistiOS's `entry.s` (previous entry) was checked against this data and found not to directly apply, which is itself reported here rather than silently discarded. ### Added — 2026-08-14 (core-cpu-sh4: LDC Rn,SR now logs at INFO level on every real SR write)
- **Confirming the previous delay-slot-diagnostic entry first**: confirmed against a real Sonic Adventure run — the `BRA -2` idle loop's delay slot is `NOP` (opcode `0x0009`), the textbook SH-4 idle-wait pattern (`bra .; nop`). This confirms the loop is genuinely "wait for a real interrupt" code with no hidden condition — `BRA` is unconditional and references no register, so the `R4=0xA05F8074` (`FPU_SHAD_SCALE`, an unrelated 3D-rendering shadow-scale register, confirmed against Flycast's `pvr_regs.h`) seen in the same register snapshot is just leftover context from earlier code, not part of any exit condition.
- Cross-referenced the real, established SH-4/Dreamcast convention for enabling interrupts against KallistiOS's own `entry.s`: `irq_enable` does `stc sr,r0 / and r1,r0 / ldc r0,sr` with `_irqe_and = 0xEFFFFF0F`, which clears **both** `BL` (bit 28) and `IMASK` (bits 7-4) in one operation. Fixed `LDC Rn,SR`'s own Javadoc, which had gone stale (still said "only bit 0 (T) is meaningful" after `BL`/`IMASK` became meaningful in a previous entry).

### Changed — 2026-08-12 (core-cpu-sh4/core-gpu-pvr2/app-cli: removed read-driven placeholders in PvrRegisters/HollySystemRegisters, replaced with real step-driven timing + this project's first real SH-4 interrupt delivery)
- **Confirming the previous HollySystemRegisters entry first**: confirmed against the real Gradle suite by the project owner — `HollySystemRegistersTest` 5/5, full suite `BUILD SUCCESSFUL` — and against a real Sonic Adventure run: both spin-waits (`SPG_STATUS` and `SB_ISTNRM`) now genuinely terminate, and execution advanced further, reaching `Unimplemented`-free but stuck code: a stable **1-instruction** loop, `BRA -2` (branches to itself) at `PC=0x8C6696A8`, real opcode `0xAFFE` (`disp12=0xFFE=-2`, confirmed `new_pc = pc+4+disp*2 = pc`), which ran for the entire 100,000,000-step budget without leaving it.
- **This is a fundamentally different kind of blocker than a register poll**: `BRA`-to-itself, right after code that set up interrupt-related hardware state, is genuine "wait for a real interrupt to preempt me" idle code. No amount of faking what a register *reads as* — which is exactly what this project's `PvrRegisters`/`HollySystemRegisters` placeholders were doing — can make that progress; it needs an actual interrupt to actually arrive.
- **This prompted removing both existing placeholders, not adding a third one for this new blocker.** On reflection, `SPG_STATUS`'s "advance on every read" and `SB_ISTNRM.VBLANK_BEGIN`'s "always pending on read" both had the same underlying problem: real hardware state that only changes because software happened to poll it isn't modeling the hardware, it's making the specific symptom that was found go away — hiding the problem rather than solving it. Both were replaced with a real mechanism instead:
  - **`PvrRegisters.tick()`**: `SPG_STATUS.scanline` now advances once per `Sh4Cpu.step()` (called by `app-cli`'s `Main`, regardless of whether anything ever reads `SPG_STATUS`), not once per read. Derived from real, cited hardware constants — SH7091/SH-4's documented `200MHz` core clock, and NTSC's standard `59.94Hz` field rate / `262`-line field length (`STEPS_PER_LINE = round(200_000_000 / 59.94 / 262) = 12,735`) — with exactly one clearly-labeled, honestly-scoped approximation: `1 step ≈ 1 real SH-4 clock cycle`, since this interpreter has no real per-instruction cycle accounting yet (a marker left for where real cycle-accurate timing, or real `SPG_LOAD`-driven timing, would replace this). `tick()` returns `true` exactly when the per-field line counter wraps back to `0`.

### Fixed — 2026-08-07 (core-cpu-sh4: SHAD/SHLD missing full sign-fill for Rm an exact multiple of ±32)
- `core-cpu-sh4`: fixed `SHAD`/`SHLD` (dynamic shift instructions). The previous implementation computed the right-shift case directly as `r[n] >> (-r[m])` / `r[n] >>> (-r[m])`, relying on Java's automatic masking of an `int` shift count to its low 5 bits to match the SH-4 spec's own `Rm & 0x1F` masking. That coincidence holds for almost every negative `Rm` value — but not when `Rm` is an exact multiple of ±32 (`-32`, `-64`, ..., down to `Integer.MIN_VALUE`): there, `-Rm` is itself a multiple of 32, so Java's masking silently reduces the shift to `>> 0` (a no-op), while the authoritative spec requires a FULL sign/zero-fill (`SHAD`: `0x00000000` or `0xFFFFFFFF` depending on `Rn`'s sign; `SHLD`: always `0x00000000`) in exactly that case.
- **Found during a dedicated `core-cpu-sh4` review pass**, not by a real disc run — this is a genuinely rare edge case (only triggered when a dynamic shift-amount register holds a value that happens to be an exact multiple of 32), so the real Sonic Adventure dump had no particular reason to have hit it yet. A previous version of this code's own comment specifically reasoned about the `Integer.MIN_VALUE` case and concluded "no special-casing is needed" — that reasoning confirmed the arithmetic coincidence (`Integer.MIN_VALUE & 0x1F == 0`, same as every other affected value) without checking it against what the spec actually requires there, and so missed that the correct result is a full fill, not a no-op.
- Confirmed against the authoritative SH opcode/pseudocode reference (`shared-ptr.com/sh_insns.html`) — the same source already used for `DIV1`'s Q/M-flag logic — before fixing: rewritten to follow that reference's own `SHAD`/`SHLD` structure directly (branch on `Rm`'s sign bit, then separately on whether `Rm & 0x1F == 0`) instead of reasoning about Java shift semantics from first principles, which is what produced the original bug.
- 4 new JUnit tests: `SHAD` with `Rm=-32` and `Rn`'s MSB clear (expects `0x00000000`) and set (expects `0xFFFFFFFF`); `SHAD` with `Rm=Integer.MIN_VALUE` (the exact case the old comment reasoned about and got wrong); `SHLD` with `Rm=-64` and `Rn`'s MSB set (expects `0x00000000` unconditionally — SHLD's fill doesn't depend on Rn's sign, unlike SHAD's). All 4 pre-existing `SHAD`/`SHLD` tests re-run and confirmed unaffected by the fix. 140 tests total in `core-cpu-sh4`.
- Found as part of a broader review of `core-cpu-sh4` requested by the project owner: catalogued all 105 opcode dispatch branches in `executeNonDelayedInstruction` and brute-force-checked all 65,536 possible 16-bit opcode values for dispatch-order shadowing bugs (an earlier, broader `if/else` branch silently claiming opcodes meant for a later, more specific one) — **found none**; the dispatch chain correctly partitions the opcode space despite its length. A restructuring proposal (extracting the dispatch into per-instruction-family methods, no semantic changes) followed on `refactor/core-cpu-sh4` — see the entry above.

### Added — 2026-07-27 (core-cpu-sh4: ROTL/ROTR/ROTCR, SHAD/SHLD, TAS.B)
