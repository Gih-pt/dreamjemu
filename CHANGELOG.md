### Changed — 2026-07-31 (app-cli: LoopDetector now stays continuously active, only re-reports a genuinely different loop)
- The previous refinement (report once, then switch detection off and keep stepping silently) was itself tested against the real Sonic Adventure dump — and reached the whole 5,000,000-step budget again, with no way to tell from that alone whether execution had stayed stuck in the exact same loop, moved on to a different one, or reached genuinely new code that just happened to run long. Ambiguous, not useful.
- Fixed by keeping `LoopDetector` continuously active instead of switching it off after the first report. A re-detection of the *same* loop — which will keep happening every ~`repeatThreshold × period` steps for as long as execution stays in it — is identified via a new `identifyLoop` helper (the lowest PC in the loop's body, reconstructed from the existing ring buffer; real compiled loops essentially never coincidentally share a lowest instruction address) and silently reset/re-armed rather than printed again. A genuinely *different* loop (different lowest PC) IS reported, with a note that the previous loop was left. A single run can now distinguish all four outcomes: stuck in one loop the whole time, moved through several distinct loops, reached new code, or hit something unimplemented.
- Two new synthetic integration checks (sandbox harnesses, not committed as JUnit — see below) confirm both directions: two genuinely different loops in sequence produce exactly 2 distinct reports at the right steps before reaching an intentionally-undefined opcode; a single loop that never exits within the budget produces exactly 1 report for the entire run, never a spurious repeat.
- *AI usage: yes — implemented with Claude (Anthropic), following the project owner's explicit direction after reviewing real, if ambiguous, output from the previous refinement. Control-flow and a simple PC-based identity heuristic only, no new opcode/format semantics, no web search needed. Verified: compiles cleanly with `javac`; both new integration harnesses pass, along with the full harness suite built up over this session (no regressions). `identifyLoop` itself is a private helper in `Main` (not yet extracted for direct JUnit coverage — `LoopDetectorTest` still only covers `LoopDetector` itself); still needs a real `./gradlew :app-cli:test` run, and a re-run of `app-cli` against the real Sonic Adventure dump with this refined behavior, to confirm end-to-end.*

### Added — 2026-07-31 (app-cli: LoopDetector — stops early on a stable repeating loop instead of exhausting the step budget)
- The real Sonic Adventure dump's 5,000,000-step run (previous entries) never hit an unimplemented instruction — a `--log-level TRACE` run (redirected to a file, 5,000,054 lines) revealed why: a tight, stable 5-instruction loop repeating identically millions of times — `MOV.B R4,@R5` / `ADD #1,R5` / `MOV.L @R6,R3` / `CMP/HS R3,R5` / `BF` back to the top. Decoded by hand: almost certainly a legitimate `crt0`-style byte-at-a-time `.bss`-clearing loop, not a spin-wait on unmodeled hardware — just far too slow to finish within any practical step budget.
- Added `LoopDetector`: tracks, per PC, the step index it was last seen at; when a PC recurs, the distance since its last occurrence is a candidate period; if that same period recurs `repeatThreshold` times in a row (`app-cli` uses 1,000), the cycle is declared stable. Requiring many *consecutive* identical-period repeats (not just one revisit) means a call/return pair or any other coincidental single address revisit can't misfire it.
- Wired into `app-cli`'s stepping loop: on detection, prints the loop's period, confirmed repeat count, and the full loop body (`PC`/`opcode` for one complete period, reconstructed from a small ring buffer), then stops — instead of continuing to burn the step budget (or a `TRACE` log) on identical repeated output.
- Verified against a synthetic reproduction of the *exact* real loop (same 5 opcodes, a destination 1,000,000 bytes from its configured limit): detected in ~1,000 steps rather than exhausting a 5,000,000-step budget, with period, repeat count, and genuine register-state progress all confirmed.
- `LoopDetector` is `app-cli`'s **first-ever unit-tested class** — pure PC-sequence logic with no dependency on `Sh4Cpu`/`Bus`/disc images, unlike the rest of the module's I/O-heavy orchestration (which still has no dedicated suite). 8 new JUnit tests.
- **Caught its own real bug during sandbox verification** (not via a real Gradle run this time — via the standalone harness, before any JUnit was involved): a `repeatThreshold == 1` edge case ("detect on the very first repeat") silently failed to detect anything, because the threshold check only ran inside the branch for a period matching an *existing* candidate, never when a brand-new candidate period was first established — which is exactly what happens on a repeat count of 1. Fixed by moving the threshold check to run after either branch.
- *AI usage: yes — implemented with Claude (Anthropic), designing the algorithm from scratch (no external spec to verify against — this is original logic, not a hardware/format detail). Verified: compiles cleanly with `javac`; a standalone sandbox harness reproducing all 8 new `LoopDetectorTest` cases initially caught the `repeatThreshold == 1` bug directly (15/16 checks passed, then 16/16 after the fix); a separate integration harness reproducing the exact real memset-loop shape confirms detection in ~1,000 steps against a 5,000,000-step budget; the full harness suite built up over this session was re-run afterward with no regressions. Still needs a real `./gradlew :app-cli:test` run, and a re-run of `app-cli` against the real Sonic Adventure dump, to confirm end-to-end.*

### Fixed — 2026-07-31 (common: LoggerTest — @BeforeEach ordering bug, test-only)
- The project owner's `./gradlew :common:test` run (the very first real run of the new logging module) failed 6 of 11 tests — every one that asserted `captured.size() == 1`, while every test asserting `captured.isEmpty()` passed.
- Root cause: `LoggerTest` split setup across two separate `@BeforeEach` methods (one resetting `LogConfig`, one separately installing a capturing `LogSink`). **JUnit5 does not guarantee execution order between multiple `@BeforeEach` methods in the same class.** When the config-reset method happened to run *after* the sink-install method, its `resetSinkToStdout()` call silently undid the capturing sink — every log record then went to real stdout instead of the test's `captured` list, so `size() == 1` assertions failed while `isEmpty()` assertions passed trivially (nothing was ever added).
- This is a **test-only bug** — `Logger`/`LogConfig`/`LogSink`/`LogRecord` themselves were never wrong; only the test's own setup ordering was. Fixed by merging both into a single `@BeforeEach` method (and a single `@AfterEach`), which has no ordering ambiguity with itself.
- Notable as a class of bug this project's sandbox verification genuinely cannot catch: the standalone hand-written harnesses used throughout this session are plain imperative `main()` methods with no lifecycle-method concept, so they never exercise JUnit-annotation-ordering behavior at all — only a real `./gradlew test` run can. This is exactly why every recent CHANGELOG entry in this project has kept flagging "still needs a real Gradle run" as a distinct, non-optional verification step rather than treating sandbox/harness checks as equivalent.
- *AI usage: yes — implemented with Claude (Anthropic), fixing a real test failure reported directly from the project owner's own `./gradlew :common:test` output. `Logger`/`LogConfig` production code is unchanged; only `LoggerTest`'s setup structure was fixed.*

### Fixed — 2026-07-31 (core-gdrom: Iso9660FileSystem misread high-density-area LBAs as track-relative — found via the same real Sonic Adventure dump)
- After the data-track-selection fix (below) opened the *right* track, `app-cli` against the real Sonic Adventure dump still couldn't find `1ST_READ.BIN`: the new diagnostic listing showed `Root directory extent: LBA 45020, 40960 bytes` but `Entries found: 0`. The `45020` was the giveaway.
- Confirmed against dreamcast.wiki's GDI format page ("Track 3 always starts at an LBA of 45000") and Redump's GD-ROM dumping documentation: a Dreamcast GD-ROM's high-density area (the real game data, as opposed to the small CD-compatible "single-density" area) always starts at absolute physical LBA 45000, and every `extentLba` value stored inside that area's own ISO9660 directory records (root directory, every file) is written using that same disc-absolute numbering — *not* renumbered relative to the extracted track, regardless of container format (GDI, CUE/BIN, CDI). `Iso9660FileSystem` was reading those values directly, so a "root directory at LBA 45020" lookup tried to read 45020 sectors into a track that's only a few tens of thousands of sectors long — nothing was there, so `listRootDirectory()` correctly (if uninformatively) found 0 entries.
- Fix: `Iso9660FileSystem.open` now detects this (a root directory `extentLba` at or past 45000 has no other plausible explanation for a track-relative filesystem) and transparently subtracts 45000 from every `extentLba` it reads afterward — the root directory's own extent and every entry found while listing it. A plain single-session disc, or the already-correctly-track-relative low-density area, is unaffected (confirmed by a regression check covering both paths).
- Added `findsAndReadsTheBootFileInsideADreamcastHighDensityArea` to `Iso9660FileSystemTest`, reproducing the exact disc-absolute-addressing layout that exposed this bug (data physically stored at small, track-relative array offsets, but `extentLba` fields written using the `45000`-based scheme) — 8 tests total in the class now.
- *AI usage: yes — implemented with Claude (Anthropic), including a web search to confirm the `45000` constant against authoritative public sources (dreamcast.wiki, Redump's dumping documentation) before using it, per this project's "verify before implementing" rule for exact format semantics. Verified: compiles cleanly with `javac`; a sandbox harness reproducing both the high-density (rebased) and low-density (unrebased) cases confirms the fix and its regression safety (all checks passed); the full existing end-to-end synthetic-disc harness from the previous update was re-run and still passes (no regression). Still needs the project owner to re-run `app-cli` against the real Sonic Adventure dump to confirm the boot file is now actually found and loaded end-to-end.*

### Fixed — 2026-07-31 (app-cli: GDI/CUE-BIN/CDI opened the wrong data track — found via a real disc image)
- Every one of `app-cli`'s three disc-format openers (`openGdiDataTrack`, `openCueBinDataTrack`, `openCdiDataTrack`) picked the **first** data track on the disc. Real Dreamcast GD-ROM images commonly have more than one: a small "single-density" area first (present only so an ordinary CD-ROM drive sees a valid-looking disc — it is not the game), then an audio track, then the real "high-density" game data as the **last** track. Picking the first track silently opened the wrong, nearly-empty filesystem instead of failing loudly.
- Found by running `app-cli` against a real Sonic Adventure (USA) GD-ROM dump (a 3-track `.cue`: `TRACK 01 MODE1/2352` single-density / `TRACK 02 AUDIO` / `TRACK 03 MODE1/2352` high-density) — `1ST_READ.BIN` couldn't be located, even though the IP.BIN header parsed perfectly (hardware ID checksum `[OK]`, correct product number, title, etc. — both areas start with a valid copy of IP.BIN, which is why the header alone didn't reveal the bug). A new diagnostic fallback (`printRootDirectoryDiagnostics`, added first to investigate rather than guess) showed the root directory it was actually reading held only the three standard ISO9660 placeholder files (`ABSTRACT.TXT`, `BIBLIOGR.TXT`, `COPYRIGH.TXT`) and an `EXTRA` directory — the exact, well-known contents of a GD-ROM's single-density area, confirming which track was being opened by mistake.
- Fix: all three openers now pick the **last** data track instead of the first — the same convention real Dreamcast tools and emulators (redream, Flycast, etc.) already rely on. `core-gdrom`'s track-resolution code itself (`CueBinImage`, `GdiImage`, `CdiImage`) needed no changes; the bug was entirely in `app-cli`'s track-selection loop.
- Added a standalone sandbox check (`GdRomTrackSelectionCheck`, not committed — no formal test infra exists for `app-cli` yet) reproducing the exact 3-track single-density/audio/high-density layout from the real `.cue` and confirming the fixed selection logic lands on track 3, not track 1.
- The diagnostic fallback added to investigate this (`Main.printRootDirectoryDiagnostics`, printing the root directory's extent and every entry found in it whenever boot-file lookup fails) is kept in place going forward, not just for this one bug.
- *AI usage: yes — implemented with Claude (Anthropic), diagnosing a real bug report from the project owner running `app-cli` against an actual disc image rather than synthetic test data. ### Added — 2026-07-30 (core-gdrom: Iso9660FileSystem.readFile; core-system: HleBootLoader; app-cli: first minimally real BIOS-free boot attempt)
- `core-gdrom`: added `Iso9660FileSystem.readFile(record)` — reads a located file's full contents off disc, sector by sector via the class's existing `SectorSource`/`LogicalSectorReader` normalization, correctly handling a partial final sector. Previously `findInRootDirectory` could only resolve a file's LBA + size, not its actual bytes; this is the missing piece needed to load a boot executable into RAM.
- `core-system`: added `HleBootLoader`, a new, deliberately narrow class that writes a boot file's bytes into any `Bus` implementation at `BOOT_FILE_ENTRY_ADDRESS` (`0x8C010000`) and returns that address as the SH-4's entry point. This is the real Dreamcast boot address — confirmed against Marcus Comstedt's "Dreamcast Programming - IP.BIN and 1ST_READ.BIN" page (mc.pp.se/dc/ip.bin.html), the same authoritative reference already cited for `IpBinHeader`'s field offsets — not a guess or an arbitrary placeholder. `HleBootLoader` intentionally does not depend on `core-gdrom` or `core-cpu-sh4`, keeping it a generic "bytes in, entry address out" utility; orchestrating it together with disc reading and the CPU is left to the caller (now `app-cli`).
- **Known, documented limitation:** real CD (non-GD-ROM) discs store `1ST_READ.BIN` "scrambled" as a scatter-load copy-protection scheme; `HleBootLoader` only does a plain, contiguous load, which is correct for GD-ROM-sourced dumps (this project's primary target) but not yet for a scrambled CD-format boot file. Noted in the class Javadoc and tracked in `docs/STATUS.md`, not silently wrong.
- `app-cli`: after locating the boot file (as before), now reads its bytes, loads them into a real `SystemBus` via `HleBootLoader`, constructs a real `Sh4Cpu` at the returned entry point, and steps it (up to a 100,000-step budget) until an unimplemented instruction stops it — reporting the exact PC and reason rather than either crashing or silently claiming success. This is the project's first end-to-end exercise of every piece built so far (IP.BIN parsing → ISO9660 lookup → disc reading → RAM loading → SH-4 execution) working together, and does **not** mean any real game runs yet — the interpreter still only covers a subset of the SH-4 ISA (no `TRAPA`, no MMU, no hardware registers), so real boot code is expected to stop quickly.

### Added — 2026-07-27 (core-cpu-sh4: ROTL/ROTR/ROTCR, SHAD/SHLD, TAS.B)
