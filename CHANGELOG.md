### Changed — 2026-08-08 (core-cpu-sh4: restructured the 105-branch opcode dispatch chain into 7 per-family methods, on `refactor/core-cpu-sh4`)
- Extracted `executeNonDelayedInstruction`'s single 105-branch `if/else` chain into 7 `private Integer tryExecuteXxx(...)` methods grouped by instruction family: `Misc`, `DataTransfer`, `Arithmetic`, `Logic`, `ShiftRotate`, `ExtendSwap`, `SystemControl`. **Purely mechanical** — every branch's opcode mask, value, and body is byte-for-byte identical to before this change, just physically relocated into the method for its family, in the same relative order within that family. `executeNonDelayedInstruction` itself now just computes `n`/`m`/`imm8`/`nextPc` and tries each family method in a fixed order, returning on the first non-`null` (boxed `Integer`) match; falls through to the same `UnsupportedOperationException` as before if none match.
- Motivation: the dispatch chain had grown one branch at a time across many real-Sonic-Adventure-disc-driven sessions (see `docs/AI_CONTINUATION.md`) to 105 sequential branches in a single method — functionally correct throughout, but increasingly hard to navigate, and every future opcode addition meant scrolling the whole thing to find the right spot.
- Before touching any code, catalogued all 105 branches and brute-force-checked all 65,536 possible 16-bit opcode values against the full dispatch chain for order-dependent shadowing bugs (an earlier, broader branch silently claiming opcodes meant for a later, more specific one). **Found none** — confirmed the original chain already correctly partitioned the opcode space, which is what makes a pure reordering-into-methods restructuring safe: no branch's outcome for any opcode can change by virtue of which method now contains it.
- A handful of individual instructions (`DIV1`, `XTRCT`, `SWAP.B`, `CMP/STR`, `MOVA`, `DIV0S`/`DIV0U`, `TAS.B`) were also spot-re-confirmed against the authoritative reference during the same review pass and found correct; `SHAD`/`SHLD` (see the entry directly below) was the one genuine bug this pass found — fixed separately, before the restructuring, so the restructuring itself carries zero semantic changes.
- Verified with the same standalone `javac`-based approach as the `SHAD`/`SHLD` fix below (`services.gradle.org` isn't in this sandbox's allowed domains, so `./gradlew` can't run here): the extraction script asserts structurally that all 105 original branches appear in the output exactly once (no duplication, none dropped) before writing the file; a 17-check manual harness — the 4 `SHAD`/`SHLD` regression tests, the 4 pre-existing `SHAD`/`SHLD` tests, and one smoke-test instruction per new family (including `TRAPA`'s special early-return path, which doesn't fall through to the common `return nextPc`) — all pass (17/17).
- *AI usage: yes — implemented with Claude (Anthropic). The extraction itself was done programmatically (a script that parses the original method's branch boundaries and reassembles them into the 7 new methods) specifically to avoid manual copy-paste transcription errors in a change this size; the script's own assertions plus the manual harness above are what were checked before delivery. Confirmed with the real `./gradlew :core-cpu-sh4:test` suite by the project owner: `Sh4CpuTest` 142/142 passing (the Gradle XML report also surfaced that the pre-restructuring baseline was actually 138 tests, not the 136 this project's docs had drifted to claiming — corrected alongside this entry), `Sh4CpuSystemBusIntegrationTest` 3/3 passing, unaffected.*

### Fixed — 2026-08-07 (core-cpu-sh4: SHAD/SHLD missing full sign-fill for Rm an exact multiple of ±32)
- `core-cpu-sh4`: fixed `SHAD`/`SHLD` (dynamic shift instructions). The previous implementation computed the right-shift case directly as `r[n] >> (-r[m])` / `r[n] >>> (-r[m])`, relying on Java's automatic masking of an `int` shift count to its low 5 bits to match the SH-4 spec's own `Rm & 0x1F` masking. That coincidence holds for almost every negative `Rm` value — but not when `Rm` is an exact multiple of ±32 (`-32`, `-64`, ..., down to `Integer.MIN_VALUE`): there, `-Rm` is itself a multiple of 32, so Java's masking silently reduces the shift to `>> 0` (a no-op), while the authoritative spec requires a FULL sign/zero-fill (`SHAD`: `0x00000000` or `0xFFFFFFFF` depending on `Rn`'s sign; `SHLD`: always `0x00000000`) in exactly that case.
- **Found during a dedicated `core-cpu-sh4` review pass**, not by a real disc run — this is a genuinely rare edge case (only triggered when a dynamic shift-amount register holds a value that happens to be an exact multiple of 32), so the real Sonic Adventure dump had no particular reason to have hit it yet. A previous version of this code's own comment specifically reasoned about the `Integer.MIN_VALUE` case and concluded "no special-casing is needed" — that reasoning confirmed the arithmetic coincidence (`Integer.MIN_VALUE & 0x1F == 0`, same as every other affected value) without checking it against what the spec actually requires there, and so missed that the correct result is a full fill, not a no-op.
- Confirmed against the authoritative SH opcode/pseudocode reference (`shared-ptr.com/sh_insns.html`) — the same source already used for `DIV1`'s Q/M-flag logic — before fixing: rewritten to follow that reference's own `SHAD`/`SHLD` structure directly (branch on `Rm`'s sign bit, then separately on whether `Rm & 0x1F == 0`) instead of reasoning about Java shift semantics from first principles, which is what produced the original bug.
- 4 new JUnit tests: `SHAD` with `Rm=-32` and `Rn`'s MSB clear (expects `0x00000000`) and set (expects `0xFFFFFFFF`); `SHAD` with `Rm=Integer.MIN_VALUE` (the exact case the old comment reasoned about and got wrong); `SHLD` with `Rm=-64` and `Rn`'s MSB set (expects `0x00000000` unconditionally — SHLD's fill doesn't depend on Rn's sign, unlike SHAD's). All 4 pre-existing `SHAD`/`SHLD` tests re-run and confirmed unaffected by the fix. 140 tests total in `core-cpu-sh4`.
- Found as part of a broader review of `core-cpu-sh4` requested by the project owner: catalogued all 105 opcode dispatch branches in `executeNonDelayedInstruction` and brute-force-checked all 65,536 possible 16-bit opcode values for dispatch-order shadowing bugs (an earlier, broader `if/else` branch silently claiming opcodes meant for a later, more specific one) — **found none**; the dispatch chain correctly partitions the opcode space despite its length. A handful of other instructions (`DIV1`, `XTRCT`, `SWAP.B`, `CMP/STR`, `MOVA`, `DIV0S`/`DIV0U`, `TAS.B`) were also re-confirmed against the same authoritative reference and found correct; `SHAD`/`SHLD` was the one genuine bug this pass found. A restructuring proposal (extracting the dispatch into per-instruction-family methods, no semantic changes) followed on `refactor/core-cpu-sh4` — see the entry above.
- *AI usage: yes — found and fixed with Claude (Anthropic), including web research to confirm the correct `SHAD`/`SHLD` algorithm against an authoritative public reference (the same one already used for `DIV1`) before writing any code, and a from-scratch brute-force opcode-overlap check across the full 16-bit opcode space. Verified with a standalone `javac`-based manual harness in a sandbox (no Gradle/Maven Central access there — `services.gradle.org` isn't reachable from this sandbox either): the 4 new regression tests and the 4 pre-existing `SHAD`/`SHLD` tests all pass (8/8). Confirmed with the real `./gradlew :core-cpu-sh4:test` suite (140/140) by the project owner before this landed on `main`.*

### Added — 2026-08-04 (core-aica: bring-up of the first per-channel and global AICA registers — first code in this module, on branch `feature/pvr2-aica-maple`)
- New module content for `core-aica` (previously an empty placeholder with only a `build.gradle.kts` stub — see `docs/ARCHITECTURE.md`). Started with the registers needed to describe "play this sample": `AicaChannelAddress` (per-channel register block address arithmetic — 64 channels, 0x80-byte stride, base `0x00800000`/ARM7 and `0xA0700000`/SH4), `AicaSampleFormat` (the 4 sample formats a channel can play), `AicaPlayControl` (offset `0x0000` within a channel — key-event, loop enable, format, sample-address-high), `AicaLoopRange` (the `LoopStart`/`LoopEnd` register pair, offsets `0x0008`/`0x000c`, modeled together since the source defines one in terms of the other), and `AicaMasterVolume` (the global `0x2800` register — the one non-per-channel register in this batch).
- Source used: "Yamaha AICA Sound System Hardware Reference v0.8" by yamato (`hitmen.c02.at/files/docs/dc/aica_v08.txt`), same host as the `core-gpu-pvr2` register source and same reason for going there first this time: `mc.pp.se/dc/hw.html` lists "Yamaha AICA sound system" in its hardware overview but — unlike every other chip in that list — never links it to a dedicated page; there is no `mc.pp.se` AICA document to check. Channel count (64) is sourced from that `mc.pp.se/dc/hw.html` overview line instead, cited explicitly in `AicaChannelAddress`'s Javadoc.
- One field's exact meaning is directly disputed by the source document itself, not just under-specified: `PlayControl`'s 2-bit `key-event` field gets two different bit-by-bit readings on the same page, and the source flags both with `(??)`. Rather than silently picking one and presenting it as fact, `AicaPlayControl` stores `keyEvent` as the raw 2-bit value and separately exposes `isKeyOn()`/`isAftertouch()` implementing the second ("other guess") reading, with the disagreement spelled out in the class Javadoc and a dedicated test (`isKeyOnAndIsAftertouchReadTheOtherGuessInterpretation`) documenting exactly which interpretation the accessors implement.
- `AicaMasterVolume` documents (but doesn't silently absorb into `decode()`) a real-hardware quirk the source calls out: this specific register "returns always 0x10 when read" rather than echoing back the last value written. `decode()` still decodes whatever raw value it's handed — the quirk is a memory/register-bank-level behavior, not something this register-value class should assume — but `DOCUMENTED_READ_BACK_VALUE` is provided for whichever future component wires up that read-back behavior to reference and test against.
- Scope deliberately narrow: 5 registers/structures out of AICA's much larger register set (envelope generator, LFO, filters, DSP, interrupts, the ARM7 control registers, etc. — most of which the source itself flags with far more `??`/uncertain fields than the ones picked here). No `Bus`/`core-system` integration, no actual sample playback/mixing logic, no ARM7 simulation. Picked the most confidently-documented, most immediately useful slice first, same principle as both `core-maple` and `core-gpu-pvr2`'s opening contributions.
- 31 new JUnit tests across 5 test classes (`AicaChannelAddressTest`, `AicaSampleFormatTest`, `AicaPlayControlTest`, `AicaLoopRangeTest`, `AicaMasterVolumeTest`), count confirmed via `grep -c '@Test'` per file (not hand-counted — see the `core-maple` entries below for why that's now standard practice here): per-channel address arithmetic across the full 64-channel range plus its boundaries, every `PlayControl` field's bit position in isolation, the disputed `key-event` field's two accessors, `LoopStart`/`LoopEnd`'s full documented range including both endpoints and the "no looping" convention, and `MasterVolume`'s mode byte including an explicitly-undocumented mode value decoding to the safer default (stereo) rather than guessing mono.
- *AI usage: yes — implemented with Claude (Anthropic), same conversation as this branch's `core-maple`/`core-gpu-pvr2` work, on branch `feature/pvr2-aica-maple`. ### Added — 2026-08-04 (core-gpu-pvr2: bring-up of the PVR2 core/Tile-Accelerator control registers — first code in this module, on branch `feature/pvr2-aica-maple`)
- New module content for `core-gpu-pvr2` (previously an empty placeholder with only a `build.gradle.kts` stub — see `docs/ARCHITECTURE.md`). Started with register-level structures rather than Tile Accelerator parameter-list parsing (the polygon/vertex data format itself), because the two authoritative sources checked for that format had table layouts that didn't extract cleanly enough to transcribe with confidence (see the note below) — the registers were the piece that could be verified properly today.
- `PvrSoftwareReset` (register `0xA05F8008`): the three independent reset lines for the VRAM bus, PVR core, and Tile Accelerator.
- `PvrTileBufferSize` (register `0xA05F813C`): the tile buffer's width/height in 32x32-pixel tiles. Works in actual tile counts rather than the hardware's raw "count minus 1" field, so callers never have to remember that encoding themselves — `encode()`/`decode()` do the translation at the boundary, the same way `MapleDeviceInfo` hides its wire-format details from `core-maple` callers.
- `TileAcceleratorListType` (enum) and `ObjectPointerBufferSize` (enum): the 5 polygon list types the Tile Accelerator sorts geometry into (opaque/opaque-modifier/translucent/translucent-modifier/punch-through polygons), and the 4 buffer-allocation sizes shared identically across all 5 of them.
- `PvrObjectPointerBufferConfig` (register `0xA05F8140`): buffer growth direction plus a per-list-type `ObjectPointerBufferSize`, using the two enums above.
- `PvrTaInit` (register `0xA05F8144`): the Tile Accelerator initialize trigger. Flagged explicitly in its own Javadoc that this register is documented as write-only ("writing to this register initiates...") with no stated read-back behavior — `decode()` exists for API symmetry and is tested, but what a real read of this register returns is this class's own assumption, not something the source confirms.
- Every register address, bit position, and field value was checked against "Guide to the PowerVR-chip of the Dreamcast" by Lars Olsson, v0.51 (`hitmen.c02.at/files/docs/dc/powervr-reg.txt`) before implementation, per this project's "verify against a public source first" rule. Note on source selection: `mc.pp.se/dc/pvr.html` (the same site used for `core-gdrom`'s `IpBinHeader` and all of `core-maple`) was checked first and covers PVR2 registers too, but several of its bit-layout tables came back from HTML-to-text extraction with merged/collapsed columns that couldn't be read back with confidence (e.g. which exact bits `TH`/`D`/`COL` occupy in the render pixel-format register). Rather than guess at a bit layout from a garbled table, the Lars Olsson document was used instead for the registers in this entry, since its bit tables are plain ASCII art and extracted cleanly. The `mc.pp.se` PVR2 registers remain unimplemented pending either a cleaner fetch of that page or cross-checking against a second source — not guessed at here.
- Scope deliberately narrow: register encode/decode only. No Tile Accelerator parameter-list format (the actual polygon/vertex data written to the TA), no `render-vulkan` integration, no `core-system`/`Bus` wiring, no tile-list binning simulation — those are natural next steps, not attempted here to keep this change reviewable and to avoid implementing the harder, less-clearly-documented parts on a guess.
- 24 new JUnit tests across 5 test classes (`PvrSoftwareResetTest`, `PvrTileBufferSizeTest`, `ObjectPointerBufferSizeTest`, `PvrObjectPointerBufferConfigTest`, `PvrTaInitTest`): each register's reset-state/zero-value behavior, every documented field's bit position and value range (including confirming the 5 `ta_opb_cfg` list-type fields don't overlap each other's bits), the tile-buffer "minus 1" encoding at its minimum (1 tile) and maximum (65536 tiles) representable values, and out-of-range rejection for both `PvrTileBufferSize` and `ObjectPointerBufferSize.fromFieldValue`. Test count confirmed by `grep -c '@Test'` per file rather than hand-counted, specifically because the previous `core-maple` entries in this file had to be corrected after a hand-counting mistake — not repeating that here.
- *AI usage: yes — implemented with Claude (Anthropic), same conversation as this branch's `core-maple` work, on branch `feature/pvr2-aica-maple`. Register layouts verified via web search/fetch against the cited source before implementation. **Same sandbox limitation as every `core-maple` entry above: no Java compiler available at all (headless JRE only, no `javac`, no network access to install one) — this code has only been hand-traced/reviewed, not compiled or executed.** Not yet confirmed with a real `./gradlew :core-gpu-pvr2:test` run — that, plus fixing whatever a real compiler finds first, is the necessary next step before relying on this for anything further.*

### Added — 2026-08-03 (core-maple: bring-up of the Maple bus packet protocol — first code in this module, on branch `feature/pvr2-aica-maple`)
- New module content for `core-maple` (previously an empty placeholder with only a `build.gradle.kts` stub — see `docs/ARCHITECTURE.md`), covering the wire-level structures needed to build and parse Maple bus frames, ahead of a real `core-system`/`Bus`-integrated device model: `MapleFunctionCode` (the function-code bit values, e.g. Controller/Memory Card/Keyboard), `MapleCommand` (the command/response code enum, positive = command/success, negative = error), `MapleAddress` (the 8-bit port+peripheral address format), `MapleFrameHeader` (the 32-bit big-endian frame header: command, recipient, sender, additional-word count), `MapleDeviceInfo` (the 28-word/112-byte `deviceinfo` response structure), and `ControllerButton`/`ControllerCondition` (the standard controller's digital-buttons + analog condition structure used by `GET_CONDITION`/`SET_CONDITION`).
- Every field layout, bit position, and command code was checked against Marcus Comstedt's authoritative "Dreamcast Programming" pages — `mc.pp.se/dc/maplebus.html` (frame structure, address format, function codes, command table, `deviceinfo` layout) and `mc.pp.se/dc/controller.html` (the controller condition structure and its digital-buttons bit table) — before writing any code, per this project's "verify against a public source first" rule (see `docs/AI_CONTINUATION.md`). Note the controller buttons bitfield is inverted from the usual convention (0 = pressed, 1 = released); `ControllerCondition.isPressed`/`withButton` account for this explicitly rather than leaving it as a trap for callers.
- One deliberate documented judgment call where the source doesn't specify a detail: `mc.pp.se/dc/maplebus.html` doesn't state the padding character used to fill unused bytes of `deviceinfo`'s fixed-width `product_name`/`product_license` strings. `MapleDeviceInfo.encode()` pads with NUL (the more common real-hardware convention); `decode()` trims either NUL or ASCII-space padding on the way back out, so it round-trips correctly regardless of which convention produced the bytes it's reading. Called out explicitly in the class Javadoc, not left implicit.
- One real bug caught and fixed during this same implementation session, before any external review: `MapleDeviceInfo` is a Java `record` with an `int[] functionData` field. A plain record's generated `equals()`/`hashCode()` compares `int[]` by reference (arrays don't override `Object`'s identity-based `equals`), which would silently report two logically-identical `MapleDeviceInfo` instances built from separate arrays as unequal. Caught by deliberately writing a test for exactly this case (`equalsComparesFunctionDataByValueNotByArrayReference`) before trusting the default record behavior, then fixed by overriding `equals()`/`hashCode()`/`toString()` explicitly with `Arrays.equals`/`Arrays.hashCode`. `functionData()`'s accessor also defensively clones on both the way in (constructor) and the way out (getter), confirmed by a dedicated mutation test.
- Scope deliberately narrow for this first contribution: encode/decode of these structures only, no `Bus`-integrated device/controller simulation yet, no DMA/transfer-descriptor modeling (`A05F6C04`/`A05F6C18`/`A05F6C80` registers, transfer descriptors) — those depend on `core-system` wiring and are natural next steps, not attempted here to keep this change reviewable.
- 34 new JUnit tests across 5 test classes (`MapleAddressTest`, `MapleCommandTest`, `MapleFrameHeaderTest`, `MapleDeviceInfoTest`, `ControllerConditionTest`): every documented command code round-trips through `fromCode`/`code()`, address encode/decode across all 4 ports and every sub-peripheral bit, frame header encode/decode including a negative (error) response code, `deviceinfo` encode/decode round-trip plus explicit big-endian (`func`/`function_data`) vs. little-endian (`standby_power`/`max_power`) byte-order checks, both padding conventions on decode, the array-equality bug fix above, and the controller condition's inverted-bitfield semantics plus its own byte-order checks.
- *AI usage: yes — implemented with Claude (Anthropic) in a new conversation dedicated to Phase 1 PowerVR2/AICA/Maple groundwork, on branch `feature/pvr2-aica-maple`, kept isolated from the parallel `main`-branch SH-4/app-cli/GD-ROM work per the project owner's instructions for this session. Field layouts and command codes verified via web search against the two `mc.pp.se` pages cited above before implementation. ### Added — 2026-08-03 (core-maple: MapleController — a simulated standard controller responding to real request frames)
- `MapleController`: takes an incoming `MapleFrameHeader` + request data and produces the actual encoded response frame a real Dreamcast controller would send, built directly on the previous entry's structures (`MapleFrameHeader`/`MapleDeviceInfo`/`ControllerCondition`/`MapleFunctionCode`). Handles `REQUEST_DEVICE_INFO` (responds `DEVICE_INFO` with its `deviceinfo` block) and `GET_CONDITION` for the Controller function (responds `DATA_TRANSFER` with `func` echoed back followed by the current `ControllerCondition`, per `mc.pp.se/dc/maplebus.html`'s command table: command 9's response parameters are "func, cond..."). - Deliberately still has no `core-system`/`Bus` dependency or DMA/transfer-descriptor simulation — this is a standalone, directly-testable request-in/response-out state machine, matching the same narrow-module principle `Sh4Cpu` follows against the generic `Bus` interface. ### Added — 2026-07-27 (core-cpu-sh4: ROTL/ROTR/ROTCR, SHAD/SHLD, TAS.B)
