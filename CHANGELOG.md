### Added — 2026-07-27 (core-cpu-sh4: ROTL/ROTR/ROTCR, SHAD/SHLD, TAS.B)
- `core-cpu-sh4`: implemented 6 new opcodes: `ROTL`, `ROTR` (plain 32-bit rotate), `ROTCR` (33-bit rotate through `T`, completing the family alongside the already-implemented `ROTCL`), `SHAD`, `SHLD` (dynamic shift by a signed register-held amount), and `TAS.B` (test-and-set).
- `SHAD`/`SHLD` are implemented directly with Java's `<<`/`>>`/`>>>` operators, which already mask their shift count to the low 5 bits for an `int` operand — exactly the SH-4 spec's own `&0x1F` behavior, including the `Rm == Integer.MIN_VALUE` edge case (`-Rm` overflows back to `MIN_VALUE` under ordinary 32-bit wraparound in both Java and real hardware, and `MIN_VALUE & 0x1F` is `0` either way, so no special-casing was needed). The only real difference between the two instructions is that `SHAD`'s right-shift is arithmetic and `SHLD`'s is logical — tested with the same negative input for both to make that concrete.
- `TAS.B @Rn` reads a byte, sets `T = (byte == 0)`, then unconditionally ORs `0x80` into it and writes it back — real hardware does this as a single locked bus cycle (a mutex primitive); this interpreter runs single-threaded, so a plain read-then-write sequence is already equivalent, noted in the code rather than left unexplained.
- All 6 opcodes cross-checked against multiple independent public sources (several different forks of QEMU's SH-4 disassembler tables, which agreed exactly on every encoding) before implementation.
- 9 new JUnit tests, including `ROTCR` tested by first setting `T` via `CMP/PZ` then confirming both halves of the 33-bit rotate (old `T` becomes new MSB, old LSB becomes new `T`), and `SHAD`/`SHLD` given the identical negative input to make their sign-extend-vs-zero-fill difference concrete rather than incidental. 113 tests total in `core-cpu-sh4`.
- *AI usage: yes — implemented with Claude (Anthropic), including web research to source and cross-check all 6 opcode encodings against multiple independent disassembler implementations before writing any code. Hand-traced every test's expected register/flag state against the implementation before handoff; needs a real `./gradlew :core-cpu-sh4:test` run to be considered validated.*

### Added — 2026-07-27 (core-cpu-sh4: comparisons, TST/DT, extend/swap/xtrct, multi-word arithmetic)
- `core-cpu-sh4`: implemented 22 new opcodes filling out the core comparison/logic/extend/multi-word-arithmetic instruction set: `CMP/HS`, `CMP/GE`, `CMP/HI`, `CMP/GT`, `CMP/PL`, `CMP/PZ`, `CMP/STR`, `TST` (register + `#imm,R0`), `DT`, `EXTS.B`/`EXTS.W`, `EXTU.B`/`EXTU.W`, `SWAP.B`/`SWAP.W`, `XTRCT`, `ADDC`, `SUBC`, `NEGC`, `ADDV`, `SUBV`.
- `CMP/HS`/`CMP/HI` (unsigned) vs `CMP/GE`/`CMP/GT` (signed) are genuinely different comparisons, not aliases of each other — tested with `-1`/`0xFFFFFFFF` specifically because it's huge unsigned but negative signed, so an implementation that accidentally used the wrong comparison would fail the test rather than coincidentally pass.
- `ADDC`/`SUBC`/`NEGC` (carry/borrow-chaining arithmetic) are implemented via a 64-bit intermediate value rather than a literal syntax port of the SH-4 manual's own algorithm, since that algorithm relies on C's unsigned-comparison semantics, which don't translate safely to a character-for-character Java port (a naive `tmp0 > tmp1` port would silently use signed comparison and be wrong). `ADDV`/`SUBV` (signed-overflow detection), by contrast, *are* a direct literal port of the manual's own same-sign-operands/different-sign-result algorithm, since that one uses only signed comparisons that translate safely as-is, and is the actual documented definition of "signed overflow" rather than something to re-derive from scratch.
- All 22 encodings sourced from the same public SH instruction set reference used for previous batches (`DIV1`, the addressing-mode batch, `RTE`), and cross-checked for opcode-space collisions against every previously-implemented instruction before adding any of them — none found.
- 24 new JUnit tests, including `ADDC`/`SUBC`/`ADDV`/`SUBV` cases matching the SH-4 manual's own worked examples (e.g. `0x7FFFFFFE + 2` overflowing to `0x80000000`) rather than arbitrary values, so the expected results are independently sourced rather than self-consistency checks. 104 tests total in `core-cpu-sh4`.
- *AI usage: yes — implemented with Claude (Anthropic), including web research to source all 22 opcode encodings and their reference pseudocode before writing any code. Hand-traced every test's expected register/flag state against the implementation before handoff (including working through the `ADDV`/`SUBV`/`ADDC`/`SUBC`/`NEGC` bit arithmetic by hand for each test case); needs a real `./gradlew :core-cpu-sh4:test` run to be considered validated.*

### Added — 2026-07-26 (core-gdrom: IpBinHeader validation + Device Info CRC-16)
- `core-gdrom`: validated every `IpBinHeader` field byte offset against Marcus Comstedt's "Dreamcast Programming - IP0000.BIN" page (mc.pp.se/dc/ip0000.bin.html) — the original, most-cited public technical reference for this header, in continuous community use since 2000. Every offset matched exactly; no changes were needed. This replaces the previous citation (an indirect, cross-referenced reconstruction, flagged provisional in `docs/STATUS.md`) with the single authoritative source directly.
- Added `IpBinHeader.calculateDeviceInfoCrc` and `IpBinHeader.embeddedDeviceInfoCrc`: the Device Information field's documented structure includes a 4-hex-digit CRC-16 checksum over the raw Product Number + Product Version bytes, so these let a caller check whether a parsed header is internally consistent — a real, meaningful validation the earlier version of this class had no way to perform. Per the source documentation, this is "exactly the same CRC algorithm as for the VMS file headers, except that the initial remainder is FFFF instead of 0," which turns out to be the standard CRC-16/CCITT-FALSE variant (poly 0x1021, init 0xFFFF, no bit reflection, no output XOR).
- The CRC algorithm itself (package-private `IpBinHeader.crc16Ccitt`) is verified directly against that variant's standard, independently-published check value (`0x29B1` for the ASCII string `"123456789"` — confirmed against an explicit passing test assertion in the `crc16` Rust crate's own test suite, not just a scraped comparison table, after an initial web search turned up a garbled/contradictory table cell for the same variant). No independently-sourced real Dreamcast product-number/version-to-CRC example was available, so the higher-level `calculateDeviceInfoCrc` method is instead checked with a full round-trip through a synthetic header (compute the CRC, write it into the header, parse the header back out, confirm the two match) — a self-consistency check, not an external validation, and documented as such.
- 4 new JUnit tests (`IpBinHeaderTest`): the CRC algorithm's standard check value, a full synthetic-header CRC round-trip, and a non-hex-digit CRC-prefix edge case. 9 tests total in `IpBinHeaderTest`.
- *AI usage: yes — implemented with Claude (Anthropic), including web research to locate the authoritative IP0000.BIN reference and to independently verify the CRC-16 variant's check value against real test-suite code rather than trusting a single scraped table (which, in this case, disagreed with the more reliable source and would have been wrong). ### Added — 2026-07-26 (core-cpu-sh4: RTE + SSR/SPC)
- `core-cpu-sh4`: implemented `RTE` (return-from-exception) plus the `SSR`/`SPC` registers it needs. `RTE` follows the same delayed-branch pattern already used for `RTS`/`JMP`/`JSR`: it reads `SSR`/`SPC` before its delay slot executes, then restores the whole Status Register from `SSR` and jumps `PC` to `SPC`.
- This interpreter has no exception/interrupt *entry* mechanism yet (no `TRAPA`, no interrupt controller, no automatic hardware save-to-SSR/SPC-and-vector-jump) — only `RTE`'s *return* path is implemented. Tests set `SSR`/`SPC` directly, the same way existing `BSR`/`JSR`/`RTS` tests already set `PR` directly without a real preceding call having happened.
- `RTE`'s opcode (`0x002B`) was confirmed against multiple independent public sources (QEMU's SH-4 disassembler tables, the fxsdk toolchain's opcode list) before implementation, rather than relying on memory alone.
- 4 new JUnit tests: jumping to `SPC` and restoring the T flag from `SSR` (overriding whatever `T` was set to immediately before `RTE` runs); the delay slot's effect being visible before the jump; `RTE` correctly rejected inside another branch's delay slot; and a branch correctly rejected inside `RTE`'s own delay slot. 80 tests total in `core-cpu-sh4`.

### Added — 2026-07-26 (core-cpu-sh4: addressing modes)
- `core-cpu-sh4`: implemented post-increment (`MOV.B/W/L @Rm+,Rn`), pre-decrement (`MOV.B/W/L Rm,@-Rn`), R0-indexed (`MOV.B/W/L @(R0,Rm),Rn` / `Rm,@(R0,Rn)`), 4-bit-displacement (`MOV.B/W @(disp,Rm),R0` / `R0,@(disp,Rn)`, `MOV.L @(disp,Rm),Rn` / `Rm,@(disp,Rn)`), and PC-relative (`MOV.W`/`MOV.L @(disp,PC),Rn`, `MOVA @(disp,PC),R0`) addressing — 21 new opcodes in total. Post-increment/pre-decrement give the interpreter the SH-4's actual push/pop idiom (`MOV.L Rm,@-R15` / `MOV.L @R15+,Rn`); PC-relative loads give it the standard way real code loads a 32-bit constant (`MOV #imm,Rn` only has an 8-bit sign-extended immediate).
- All 21 encodings were checked against a public SH instruction set reference (the same source used for `DIV1` previously) before implementation, including two details easy to get wrong from intuition alone: post-increment loads must **skip** the increment when the destination and address registers are the same register (per the spec's own `if (n != m) R[m] += ...`), and `MOV.L`/`MOVA`'s PC-relative addressing must mask the PC's low 2 bits to a longword boundary **before** adding the displacement, regardless of this instruction's own alignment.
- **A real bit-layout bug was caught by this source cross-check before any test was run**: `MOV.B/W R0,@(disp,Rn)`'s single register field sits at bits 4-7 of the opcode (this codebase's `m`), not bits 8-11 (`n`) — easy to get backwards since the spec's own mnemonic calls that field "Rn", but what determines correctness is the bit position matching this interpreter's existing `n`/`m` extraction, not the name the spec happens to use for it. Caught and fixed during implementation, before it ever reached committed code.
- 24 new JUnit tests (`Sh4CpuTest`), including: the `n==m` post-increment edge case; a full push-then-pop round trip; and a PC-relative-load test that deliberately places the instruction at a non-4-aligned address to confirm the masking behavior. 76 tests total in `core-cpu-sh4`.
- **Test bug caught and fixed by the project owner's real test run**: the PC-relative-masking test originally wrote two different 4-byte sentinel values at addresses 4 and 6 to contrast the masked-vs-unmasked target — but those two 4-byte read windows overlap by 2 bytes, so the second write corrupted the first. Fixed by relying on the (untouched, default-zero) memory at the wrong address instead of a second, corrupting sentinel write. The interpreter code itself was correct; only the test's memory layout was buggy — 73/74 passed on the first real run, 76/76 after this fix.
- *AI usage: yes — implemented with Claude (Anthropic), including web research to source all 21 opcode encodings from a public SH instruction set reference before writing any code (the cross-check that caught the bit-layout bug above). Hand-traced against each test's expected register/memory state before handoff; the project owner then ran `./gradlew :core-cpu-sh4:test` on their own machine (JDK 21, Gradle 8.7), which caught the overlapping-write test bug described above — fixed and reconfirmed passing 76/76 on the same machine.*

### Added — 2026-07-25 (core-gdrom: CUE/BIN sector reading)
- `core-gdrom`: implemented `CueTrackMode`, `CueTrack`, and `CueBinImage` — parses a `.cue` sheet's `FILE "name" BINARY` / `TRACK NN <mode>` / `INDEX 01 MM:SS:FF` lines and reads sector data from the referenced `.bin` file(s) (resolved relative to the `.cue`'s directory), following the same overall structure as `GdiImage`/`GdiTrack`. Unlike GDI, a CUE sheet doesn't declare each track's global LBA or sector count directly, so `CueBinImage` derives both: a track's sector count comes from the gap to the next track's `INDEX 01` in the same file, or from the file's remaining byte size for the last track referencing it; global LBA is the running total of every earlier track's sector count (track 1 starts at LBA 0, matching the numbering already used by `GdiImage`). Supports both common real-world layouts (multiple tracks sharing one `.bin`, and one `.bin` per track).
- The `MM:SS:FF` → frame conversion was checked against public CUE sheet format references (Hydrogenaudio's Cue Sheet wiki page, GNU ccd2cue's manual, and libyal/libodraw's CUE sheet format documentation) before implementation. The useful detail this confirmed: a CUE sheet's `INDEX` timestamp is relative to the *start of its own FILE*, with **no 150-sector (2-second) lead-in offset** — that offset only applies to whole-disc absolute MSF addressing (where `00:02:00` = LBA 0), not to file-relative CUE indexes (where `00:00:00` = the first byte of the file). Getting this backwards would have silently shifted every computed sector count and file offset by 150 sectors.
- 10 new JUnit tests (`CueBinImageTest`): track-list resolution (LBA/sector-count/mode/filename), sector reads spanning two tracks sharing one file, sector reads across two separate per-track files, an out-of-range LBA, a missing referenced `.bin` file, a track with no `INDEX 01`, an unsupported `FILE` type (non-`BINARY`), an unrecognized track mode, and a file size that isn't a whole number of sectors. 25 tests total in `core-gdrom` (15 existing + 10 new).
- **Bug caught and fixed by the project owner's real test run**: the parser tracked the "current FILE" as a single mutable variable and only associated it with a track when that track was finalized (at the *next* TRACK line or EOF) — so for a CUE sheet with one FILE per track, by the time track 1 was finalized, `currentFileName` had already been overwritten by the second FILE line, and track 1 ended up pointing at track 2's .bin file. Fixed by capturing each track's fileName at the moment its own TRACK line is parsed (`trackFileNameInProgress`), rather than re-reading the shared `currentFileName` later. This is exactly the multi-FILE-section case exercised by `readsBothTracksWithOneFileEach`, which failed before the fix (24/25 passing) and passes after it (25/25).
- *AI usage: yes — implemented with Claude (Anthropic), including web searches to confirm the CUE `INDEX`-timestamp-to-frame-count convention (and the no-150-offset detail specifically) against public documentation before coding it. Initial implementation and its test suite were only reasoned through by hand in a sandbox with no JDK at all — the project owner then ran `./gradlew :core-gdrom:test` on their own machine (JDK 21, Gradle 8.7), which caught the multi-FILE fileName bug described above; the fix was made and confirmed passing (25/25) with the same command.*

### Added — 2026-07-23
- `core-cpu-sh4`: SH-4 interpreter bring-up. Implemented `Sh4Cpu` (register file R0-R15, PC, PR, a T-flag-only status register) with a `step()` fetch-decode-execute loop, working against the generic `Bus` interface from `core-system` (not coupled to `SystemBus`/`DreamcastAddressMap`, so the interpreter can be tested and eventually reused independent of the Dreamcast-specific memory map).
