### Added — 2026-07-25 (core-gdrom: CDI sector reading)
- `core-gdrom`: implemented `CdiTrackMode`, `CdiTrack`, and `CdiImage` for DiscJuggler `.cdi` images. Unlike GDI/CUE, a CDI image is a single monolithic file: an 8-byte trailer (`{version, header_offset}`) at the very end of the file points at a binary header (session count, then each session's track count and per-track records) describing every track's data, which — unlike CUE — includes each track's global LBA and sector count explicitly, so nothing needs to be derived the way `CueBinImage` derives them. Supports CDI v2/v3/v3.5 (version markers `0x80000004`/`0x80000005`/`0x80000006`); v3.5 measures its header offset backward from the end of the file instead of forward from the start, and v3+ track records carry a few extra fields v2 doesn't.
- This class's parsing logic (field order, sizes, and the fixed 20-byte "track start" marker) was checked against the structural facts documented by the open-source DreamShell project's DiscJuggler CDI reader (`include/isofs/cdi.h`, `modules/isofs/cdi.c`, by SWAT / dc-swat.ru) before implementation — a binary container layout, which (like the CUE format facts used for the previous entry) is functional/structural information rather than creative expression. The Java code here was written independently, in this project's own style; nothing was copied from that project's source.
- **Bug found and fixed in `DiscImageDetector`, uncovered while implementing this**: `looksLikeCdi` checked the file's actual last 4 bytes as the CDI "version marker", but the real trailer is `{version(4 bytes), header_offset(4 bytes)}` in that order — so the true last 4 bytes are `header_offset` (an arbitrary file position that varies per file), and the version marker sits 4 bytes *before* those. `DiscImageDetectorTest`'s existing CDI test passed anyway only because it wrote a fake 4-byte trailer instead of a real 8-byte one, so it never exercised the mistake. Fixed the detector to read the correct 4-byte window, corrected the recognized version constants to match the sourced reference (`0x80000004`/`0x80000005`/`0x80000006`, not the previous, unsourced `0x00000004`/`0x80000004`/`0x80000005`), fixed the existing test to build a real 8-byte trailer, and added a regression test (`doesNotMistakeHeaderOffsetForVersionMarker`) proving a header_offset value that happens to look like a version marker isn't misread as one.
- 9 new JUnit tests (`CdiImageTest`): track-list resolution across one and two sessions, sector reads within a track and across sessions at distinct LBAs, an out-of-range LBA, a too-short file, an unrecognized version marker, an invalid header offset, a missing/corrupt track-start marker, and an invalid mode/sector-size-code combination. Plus 1 new regression test in `DiscImageDetectorTest` (above). `core-gdrom` now has 35 tests total (25 existing + 9 CDI + 1 detector regression).
- *AI usage: yes — implemented with Claude (Anthropic), including web research to source the CDI binary layout from the DreamShell project's public reader before writing any code, and to double check that source's own header/struct definitions (field types/sizes) rather than assuming them. Two commits' dates in this CHANGELOG (`c0b3ebc`, `07bc938`) were also corrected today from 2026-07-21 to 2026-07-20 to match GitHub's actual recorded commit dates, at the project owner's request. **Not run against a real JDK/Gradle in this session**: this sandbox still had no `javac`/JDK available (see the CUE/BIN entry below for the same limitation), so — having been burned by a real bug that only surfaced once actual tests ran, on the CUE/BIN work — this implementation was instead hand-traced byte-by-byte against each test fixture's expected file offsets and LBAs before being handed off. This still needs a real `./gradlew :core-gdrom:test` run to be considered validated, the same as CUE/BIN did.*

### Added — 2026-07-25 (core-gdrom: CUE/BIN sector reading)
- `core-gdrom`: implemented `CueTrackMode`, `CueTrack`, and `CueBinImage` — parses a `.cue` sheet's `FILE "name" BINARY` / `TRACK NN <mode>` / `INDEX 01 MM:SS:FF` lines and reads sector data from the referenced `.bin` file(s) (resolved relative to the `.cue`'s directory), following the same overall structure as `GdiImage`/`GdiTrack`. Unlike GDI, a CUE sheet doesn't declare each track's global LBA or sector count directly, so `CueBinImage` derives both: a track's sector count comes from the gap to the next track's `INDEX 01` in the same file, or from the file's remaining byte size for the last track referencing it; global LBA is the running total of every earlier track's sector count (track 1 starts at LBA 0, matching the numbering already used by `GdiImage`). Supports both common real-world layouts (multiple tracks sharing one `.bin`, and one `.bin` per track).
- The `MM:SS:FF` → frame conversion was checked against public CUE sheet format references (Hydrogenaudio's Cue Sheet wiki page, GNU ccd2cue's manual, and libyal/libodraw's CUE sheet format documentation) before implementation. The useful detail this confirmed: a CUE sheet's `INDEX` timestamp is relative to the *start of its own FILE*, with **no 150-sector (2-second) lead-in offset** — that offset only applies to whole-disc absolute MSF addressing (where `00:02:00` = LBA 0), not to file-relative CUE indexes (where `00:00:00` = the first byte of the file). Getting this backwards would have silently shifted every computed sector count and file offset by 150 sectors.
- 10 new JUnit tests (`CueBinImageTest`): track-list resolution (LBA/sector-count/mode/filename), sector reads spanning two tracks sharing one file, sector reads across two separate per-track files, an out-of-range LBA, a missing referenced `.bin` file, a track with no `INDEX 01`, an unsupported `FILE` type (non-`BINARY`), an unrecognized track mode, and a file size that isn't a whole number of sectors. 25 tests total in `core-gdrom` (15 existing + 10 new).
- **Bug caught and fixed by the project owner's real test run**: the parser tracked the "current FILE" as a single mutable variable and only associated it with a track when that track was finalized (at the *next* TRACK line or EOF) — so for a CUE sheet with one FILE per track, by the time track 1 was finalized, `currentFileName` had already been overwritten by the second FILE line, and track 1 ended up pointing at track 2's .bin file. Fixed by capturing each track's fileName at the moment its own TRACK line is parsed (`trackFileNameInProgress`), rather than re-reading the shared `currentFileName` later. This is exactly the multi-FILE-section case exercised by `readsBothTracksWithOneFileEach`, which failed before the fix (24/25 passing) and passes after it (25/25).
- *AI usage: yes — implemented with Claude (Anthropic), including web searches to confirm the CUE `INDEX`-timestamp-to-frame-count convention (and the no-150-offset detail specifically) against public documentation before coding it. Initial implementation and its test suite were only reasoned through by hand in a sandbox with no JDK at all — the project owner then ran `./gradlew :core-gdrom:test` on their own machine (JDK 21, Gradle 8.7), which caught the multi-FILE fileName bug described above; the fix was made and confirmed passing (25/25) with the same command.*

### Added — 2026-07-24 (multiply/divide instructions)
- `core-cpu-sh4`: added multiply (`MUL.L`, `MULS.W`, `MULU.W`, `DMULS.L`, `DMULU.L`), divide (`DIV0U`, `DIV0S`, `DIV1`), and `ROTCL`, plus new `mach`/`macl` registers and `Q`/`M` flags to support them. `DIV1`'s exact semantics were verified against a public SH instruction set reference before implementation ([shared-ptr.com/sh_insns.html](https://shared-ptr.com/sh_insns.html)) — this caught **two inverted-ternary bugs** in the `Q` flag update logic during development (in the branches handling the "old Q was set" case) that would otherwise have silently produced wrong division results roughly half the time. Verified correct with two full end-to-end runs of the documented 32-bit unsigned division routine (`DIV0U` + 32×`{ROTCL; DIV1}` + final `ROTCL`), each checked against independently-computed correct quotients (100/7=14, 1000000/3=333333) — a much stronger signal than testing `DIV1` in isolation. `RTE` remains deliberately unimplemented (see the previous entry). 11 new JUnit tests; 52 tests total in `core-cpu-sh4`.
- *AI assistance: yes — implemented with Claude (Anthropic), including web searches to verify the exact DIV1 algorithm against a public reference before coding it, tested locally with a JDK-based manual verification harness in a sandbox (no Gradle/Maven Central access there); needs confirmation via `./gradlew :core-cpu-sh4:test` on a real machine.*

### Added — 2026-07-24 (JMP, MOV.B/MOV.W, NOT/NEG)
- `core-cpu-sh4`: added `JMP @Rn` (delayed unconditional jump through a register, reusing `JSR`'s "read target before delay slot" discipline, but correctly not touching `PR` — tested with a `PR` sentinel), `MOV.B`/`MOV.W` load/store (byte and 16-bit word memory access, both sign-extending on load — previously only 32-bit `MOV.L` existed), and `NOT`/`NEG` (bitwise complement, two's-complement negation). `RTE` deliberately not implemented yet — it needs `SSR`/`SPC` and exception-mode state this interpreter doesn't model, so it's tracked alongside MMU/exceptions rather than stubbed out with no real behavior. 7 new JUnit tests; 41 tests total in `core-cpu-sh4`.
- *AI assistance: yes — implemented with Claude (Anthropic), tested locally with a JDK-based manual verification harness in a sandbox (no Gradle/Maven Central access there); needs confirmation via `./gradlew :core-cpu-sh4:test` on a real machine.*

### Added — 2026-07-24 (BSR/JSR/RTS subroutine call/return)
- `core-cpu-sh4`: added `BSR` (PC-relative subroutine call), `JSR` (register-indirect subroutine call), and `RTS` (return), reusing and extending the delay-slot mechanism already built for `BRA`. `BSR`/`JSR` set `PR` to the return address before running their delay slot; `RTS` jumps to `PR` after its own delay slot. `JSR` specifically reads its target register *before* the delay slot executes (matching real hardware) — tested with a delay slot that overwrites the target register itself, confirming the jump still uses the pre-delay-slot value while the delay slot's own effect is still visible. Illegal-slot-instruction detection now covers `BSR`/`JSR`/`RTS` too. 5 new JUnit tests, including a full call/return round-trip integration test; 34 tests total in `core-cpu-sh4`.
- *AI assistance: yes — implemented with Claude (Anthropic), tested locally with a JDK-based manual verification harness in a sandbox (no Gradle/Maven Central access there); needs confirmation via `./gradlew :core-cpu-sh4:test` on a real machine.*

### Added — 2026-07-23 (AND/OR/XOR and shift instructions)
- `core-cpu-sh4`: added `AND`/`OR`/`XOR` (register-register and R0-immediate forms) and `SHLL`/`SHLR`/`SHAL`/`SHAR` shift instructions to `Sh4Cpu`. The R0-immediate logic ops are correctly zero-extended (not sign-extended like `MOV`/`ADD`/`CMP`'s immediates) — a classic interpreter bug if missed, so tests specifically check this with values that would produce a different (wrong) result if sign-extension were used by mistake. `SHLR` (logical, zero-fill) and `SHAR` (arithmetic, sign-fill) are tested against the same starting value to make the difference explicit; `SHAL` is confirmed identical to `SHLL`, matching real hardware. All new instructions set the T flag from the bit shifted out where applicable. 10 new JUnit tests; 29 tests total in `core-cpu-sh4`.
- *AI assistance: yes — implemented with Claude (Anthropic), tested locally with a JDK-based manual verification harness in a sandbox (no Gradle/Maven Central access there); needs confirmation via `./gradlew :core-cpu-sh4:test` on a real machine.*

### Added — 2026-07-23 (delay slots)
- `core-cpu-sh4`: implemented delay-slot execution for `BRA`, the only delayed-branch instruction implemented so far. Restructured `Sh4Cpu.step()` into a top-level dispatcher (handling `BRA`'s delay slot specially) plus a shared `executeNonDelayedInstruction` used both for ordinary instructions and for the delay-slot instruction itself. The instruction at `PC+2` now correctly executes *before* the jump takes effect, matching real SH-4 hardware, instead of the branch happening immediately as before. Placing a branch instruction in a delay slot (illegal on real hardware) now throws `IllegalStateException` rather than silently producing wrong behavior. `BT`/`BF` are unaffected (they're correctly non-delayed on real hardware too). 3 new JUnit tests added (delay-slot execution order, illegal-slot-instruction detection) plus updates to the existing BRA test to include the now-required delay-slot instruction; 16 tests total in `core-cpu-sh4`.
- This closes the "delay slots not implemented" limitation flagged as a critical accuracy gap in the previous entry below.
- *AI assistance: yes — implemented with Claude (Anthropic), tested locally with a JDK-based manual verification harness in a sandbox (no Gradle/Maven Central access there); needs confirmation via `./gradlew :core-cpu-sh4:test` on a real machine.*

### Added — 2026-07-23
- `core-cpu-sh4`: SH-4 interpreter bring-up. Implemented `Sh4Cpu` (register file R0-R15, PC, PR, a T-flag-only status register) with a `step()` fetch-decode-execute loop, working against the generic `Bus` interface from `core-system` (not coupled to `SystemBus`/`DreamcastAddressMap`, so the interpreter can be tested and eventually reused independent of the Dreamcast-specific memory map). Implements 12 instructions: `NOP`, `MOV #imm,Rn`, `MOV Rm,Rn`, `ADD #imm,Rn`, `ADD Rm,Rn`, `SUB Rm,Rn`, `CMP/EQ Rm,Rn`, `CMP/EQ #imm,R0`, `BT`, `BF`, `BRA`, `MOV.L Rm,@Rn`/`MOV.L @Rm,Rn`. Unimplemented opcodes throw `UnsupportedOperationException` with the opcode and PC, by design. **Known limitation, tracked as follow-up work: delay slots are not implemented** (BRA branches immediately instead of executing the following instruction first, unlike real SH-4 hardware) — this must be fixed before real code can run correctly. 13 JUnit tests added, covering every implemented instruction plus an integration test: a hand-assembled loop program summing 5+4+3+2+1 via real conditional branching, storing the result to memory, and reading it back (25 CPU steps, verified against both the register and memory state).
- *AI assistance: yes — implemented with Claude (Anthropic), tested locally with a JDK-based manual verification harness in a sandbox (no Gradle/Maven Central access there); needs confirmation via `./gradlew :core-cpu-sh4:test` on a real machine.*

### Fixed — 2026-07-22 (commit `d0464cf`)
- `app-javafx`: fixed "Error: JavaFX runtime components are missing, and are required to run this application" when launching the `jpackage` app-image. - **Confirmed working end-to-end on Linux**: the packaged native binary (`app-javafx/build/jpackage/DreamJEmu/bin/DreamJEmu`) launches standalone (no Gradle, no manually-set `JAVA_HOME`) and correctly shows the bootstrap window.
