- [x] **`core-gdrom`: CUE/BIN sector reading implemented.**
  - `CueTrackMode`: the sector-size-bearing track modes seen in real CUE sheets (`AUDIO`, `MODE1/2048`, `MODE1/2352`, `MODE2/2048`, `MODE2/2336`, `MODE2/2352`), parsed case-insensitively from a TRACK line's mode token.
  - `CueTrack`: a resolved track record — global start LBA, sector count, mode, and the `.bin` file name/byte offset where its data begins — analogous to `GdiTrack` but with the LBA and sector count *computed* rather than read directly, since CUE sheets don't declare either.
  - `CueBinImage`: parses `FILE "name" BINARY` / `TRACK NN <mode>` / `INDEX 01 MM:SS:FF` lines (ignoring metadata-only lines like `REM`/`TITLE`/`PREGAP`/etc.), resolves `.bin` files relative to the `.cue` file's directory, and implements `readSector(long lba, byte[] dest)` following the exact same lazy-open-per-file pattern as `GdiImage`.
  - A track's sector count is derived, not declared: the gap to the next track's `INDEX 01` within the same file (or the remaining bytes in the file, for the last track referencing it, divided by that track's sector size). Global LBA is the running total of every earlier track's sector count, so track 1 starts at LBA 0 — consistent with the whole-disc LBA numbering already used by `GdiImage`.
  - **The exact `MM:SS:FF` → frame conversion (no 150-sector/2-second lead-in offset for CUE-sheet-relative indexes, unlike whole-disc absolute MSF addressing) was verified against public CUE sheet format documentation before implementation** (see the CHANGELOG entry for sources) — this confirmed the file-relative index value is directly usable as a sector count within its `FILE`, with no adjustment needed.
  - Supports both common real-world layouts: multiple tracks sharing one `.bin` file, and one `.bin` file per track.
  - Covers error cases: missing `INDEX 01`, a `TRACK` line before any `FILE` line, an unsupported `FILE` type (only `BINARY` is supported — no audio-file-based cue sheets), a malformed/unknown track mode, a missing referenced `.bin` file, and a file size that isn't a whole number of sectors for the mode declared.
  - 10 new JUnit tests (`CueBinImageTest`); together with the existing 15, `core-gdrom` now has 25 tests. **Confirmed passing** with `./gradlew :core-gdrom:test` on a real machine (JDK 21, Gradle 8.7) — see the CHANGELOG entry, including a real parser bug the test run caught and fixed before this was true.
- [x] **`core-gdrom`: CDI (DiscJuggler) sector reading implemented.**

Fixed the detector to check the correct window and corrected the version constants to match the sourced reference. - [x] **`core-cpu-sh4`: SH-4 interpreter bring-up — first testable instruction subset implemented and tested.**
  - `Sh4Cpu`: register file (R0-R15), PC, PR, a T-flag-only status register, and a `step()` fetch-decode-execute loop against the generic `Bus` interface from `core-system` (deliberately NOT coupled to `SystemBus`/`DreamcastAddressMap` — the interpreter should work against any Bus implementation).

- [x] **`core-cpu-sh4`: added `BSR`/`JSR`/`RTS` subroutine call/return, all with correct delay-slot semantics.**
  - `BSR label` and `JSR @Rn` set `PR` to the return address and jump to their target (a PC-relative displacement for `BSR`, a register value for `JSR`) after executing their delay slot, reusing the same delay-slot mechanism built for `BRA`. `RTS` jumps to `PR` after its own delay slot.
  - `JSR` specifically reads its target register **before** the delay slot executes, matching real hardware — verified by a test where the delay slot instruction itself overwrites that register, confirming the interpreter uses the old value for the jump target while still executing the delay slot's effect.
  - Illegal-slot-instruction detection (a branch inside a delay slot) now also covers `BSR`/`JSR`/`RTS`, not just `BRA`.

- [x] **`core-cpu-sh4`: added `JMP`, `MOV.B`/`MOV.W`, and `NOT`/`NEG`.**
  - `JMP @Rn` — delayed unconditional jump through a register, reusing the same "read target before delay slot" discipline as `JSR`, but correctly does **not** touch `PR` (unlike `JSR`) — tested with a `PR` sentinel value to confirm.
  - `MOV.B`/`MOV.W` load/store — byte and 16-bit word memory access (previously only `MOV.L`, 32-bit, existed), both sign-extending on load. Tested with values that would look wrong if sign-extension were missed.

  - `RTE` (return from exception) is deliberately **not** implemented yet — it needs `SSR`/`SPC` (saved status register / saved PC) and real exception/interrupt-mode state that don't exist in this interpreter yet; implementing it now would just be a stub with no meaningful behavior. Tracked alongside MMU/exceptions in "not started yet" below.

- [x] **`core-cpu-sh4`: added multiply (`MUL.L`/`MULS.W`/`MULU.W`/`DMULS.L`/`DMULU.L`) and divide (`DIV0U`/`DIV0S`/`DIV1`) instructions, plus `ROTCL`.**
  - Added `mach`/`macl` registers (multiply-accumulate result) and the `Q`/`M` division flags, alongside the existing `T` flag.
  - `MUL.L` truncates to 32 bits (`MACL` only); `MULS.W`/`MULU.W` operate on the low 16 bits of each register (sign- vs zero-extended respectively — tested explicitly, since mixing these up is a classic bug); `DMULS.L`/`DMULU.L` produce a full 64-bit result in `MACH:MACL`, implemented via 64-bit Java `long` arithmetic rather than the reference 32-bit-limb algorithm (simpler, mathematically equivalent).
  - `DIV0U`/`DIV0S`/`DIV1` implement the SH-4's bit-serial division primitive. **The exact `DIV1` semantics (including subtle unsigned-comparison behavior for the internal borrow/carry check) were verified against a public SH instruction set reference before implementation** — this caught two inverted-ternary bugs during development that would otherwise have silently produced wrong division results in about half of all cases.
  - **Verified with the actual documented 32-bit unsigned division routine** (`DIV0U` + 32×`{ROTCL; DIV1}` + a final `ROTCL`, matching the reference example) run end-to-end for two different dividend/divisor pairs, each checked against the independently-computed correct quotient (`100/7=14`, `1000000/3=333333`) — a much stronger correctness signal than testing `DIV1` in isolation alone, since a remaining subtle bug would very likely make a real 32-iteration division produce a wrong answer.
  - 11 new JUnit tests, including the full division routine; 52 tests total in `core-cpu-sh4`.
- [x] **`core-cpu-sh4`: added post-increment/pre-decrement, indexed, 4-bit-displacement, and PC-relative addressing modes for `MOV.B`/`MOV.W`/`MOV.L`, plus `MOVA`.**
  - `MOV.B/W/L @Rm+,Rn` (post-increment load) and `MOV.B/W/L Rm,@-Rn` (pre-decrement store) — the SH-4's pop/push idiom (e.g. `MOV.L Rm,@-R15` / `MOV.L @R15+,Rn`), tested end-to-end with a push-then-pop round trip. Post-increment correctly **skips** the increment when the destination and address registers are the same (`if (n != m) R[m] += ...`, per the spec) — tested explicitly, since assuming "always increment" would silently break in exactly that case.
  - `MOV.B/W/L @(R0,Rm),Rn` / `Rm,@(R0,Rn)` (R0-indexed addressing).
  - `MOV.B/W/L @(disp,Rm),R0` / `R0,@(disp,Rn)` (byte/word, R0-only, 4-bit displacement not scaled/×2) and `MOV.L @(disp,Rm),Rn` / `Rm,@(disp,Rn)` (longword, general register, 4-bit displacement ×4) — good for nearby struct-field access.
  - `MOV.W`/`MOV.L @(disp,PC),Rn` (PC-relative loads — the standard way to load a 32-bit constant, since `MOV #imm,Rn` only has an 8-bit sign-extended immediate) and `MOVA @(disp,PC),R0` (loads the effective address itself, e.g. for string/data literals). `MOV.L`/`MOVA` mask the PC's low 2 bits to a longword boundary **before** adding the displacement, per the spec — tested with the instruction deliberately placed at a non-4-aligned address, with different sentinel values at the correctly-masked vs. naively-unmasked target addresses, to make it unambiguous which formula was actually used.
  - All 21 new opcode encodings were checked against a public SH instruction set reference before implementation (same source used for `DIV1` previously). **A real bit-layout bug was caught by this cross-check before any test was even run**: `MOV.B/W R0,@(disp,Rn)`'s one register field sits at bits 4-7 (this codebase's `m`), not bits 8-11 (`n`) as its `...,Rn` mnemonic naming might suggest — an easy mistake, since what matters is the bit position, not what the spec calls the field.
  - 24 new JUnit tests; 76 tests total in `core-cpu-sh4`.
- [x] **`core-cpu-sh4`: added `RTE` (return-from-exception), plus the `SSR`/`SPC` registers it needs.**
  - `SSR` (Saved Status Register) and `SPC` (Saved Program Counter): on real hardware these are written automatically by exception/interrupt entry hardware and read back by `RTE`. This interpreter has no exception/interrupt *entry* mechanism yet (no `TRAPA`, no interrupt controller, no automatic save-and-vector-jump) — only `RTE`'s *return* path is implemented, so tests set `SSR`/`SPC` directly, the same way existing `BSR`/`JSR`/`RTS` tests set `PR` directly without a real preceding call.
  - `RTE` follows the same delayed-branch pattern as `RTS`/`JMP`/`JSR`: it reads `SSR`/`SPC` before its delay slot executes, then (after the delay slot) restores the whole Status Register from `SSR` and jumps `PC` to `SPC`. Correctly rejected inside another branch's delay slot, and correctly rejects a branch placed in its own delay slot, matching every other delayed branch already implemented.
  - Opcode (`0x002B`) confirmed against multiple independent public sources (QEMU's SH-4 disassembler tables, the fxsdk toolchain) before implementation.
  - 4 new JUnit tests; 80 tests total in `core-cpu-sh4`.
- [x] **`core-cpu-sh4`: filled out the remaining core comparison/logic/extend/multi-word-arithmetic instructions — 22 new opcodes.**
  - Comparisons: `CMP/HS`, `CMP/GE` (unsigned/signed `>=`), `CMP/HI`, `CMP/GT` (unsigned/signed `>`), `CMP/PL`, `CMP/PZ` (signed `>0`/`>=0`), `CMP/STR` (any-byte-equal, useful for string length/matching). `CMP/HS` vs `CMP/GE` and `CMP/HI` vs `CMP/GT` are genuinely different operations (unsigned vs signed), not aliases — tested with a value (`-1` / `0xFFFFFFFF`) chosen specifically to disagree between the two interpretations.
  - `TST` (register and `#imm,R0` forms) and `DT` (decrement-and-test — the SH-4's loop-counter idiom, paired with `BF` to loop while nonzero).
  - `EXTS.B`/`EXTS.W` (sign-extend) and `EXTU.B`/`EXTU.W` (zero-extend) a register's low byte/word to 32 bits; `SWAP.B`/`SWAP.W` (swap byte/half-word halves) and `XTRCT` (extract the middle 32 bits of two registers treated as a 64-bit pair).
  - `ADDC`/`SUBC` (add/subtract with carry/borrow chaining, for arithmetic wider than 32 bits) and `NEGC` (two's-complement negate with borrow) — implemented via 64-bit intermediate arithmetic rather than a literal port of the manual's unsigned-comparison-based algorithm, since C's implicit unsigned semantics don't translate safely to a literal syntax port in Java; `ADDV`/`SUBV` (signed-overflow-detecting add/subtract) — implemented as a direct, literal port of the manual's own same-sign-operands/different-sign-result algorithm instead, since that one *does* translate safely (all signed `long`/`int` comparisons) and is the actual documented definition of "signed overflow" here rather than something worth re-deriving.
  - All 22 encodings sourced from the same public SH instruction set reference used for previous instruction batches, cross-checked for opcode-space collisions against every previously-implemented instruction before adding (none found).
  - 24 new JUnit tests, including: `ADDC`/`SUBC` carry/borrow-chain examples matching the SH-4 manual's own worked 64-bit arithmetic examples, `ADDV`/`SUBV` boundary-value overflow cases (`0x7FFFFFFE + 2`, etc.) also from the manual's own examples, and `CMP/STR` both matching and non-matching cases. 104 tests total in `core-cpu-sh4`.
- [x] **`core-cpu-sh4`: completed the rotate/shift family (`ROTL`, `ROTR`, `ROTCR`) and added `SHAD`/`SHLD` (dynamic shifts) and `TAS.B` (test-and-set) — 6 new opcodes.**
  - `ROTL`/`ROTR` (plain, non-`T`-chained 32-bit rotate) and `ROTCR` (33-bit rotate through `T`, the mirror image of the already-implemented `ROTCL`) — `ROTCR` tested by first setting `T` via `CMP/PZ`, then confirming both halves of the rotate: the *old* `T` becomes the new MSB, and the *old* LSB becomes the new `T`.
  - `SHAD`/`SHLD` (shift dynamically by a register-held signed amount — positive shifts left, negative shifts right, zero is a no-op): the only real difference between them is that `SHAD`'s right-shift is arithmetic (sign-extending) and `SHLD`'s is logical (zero-filling), tested with the same negative input value for both to make that difference concrete. Implemented directly with Java's `<<`/`>>`/`>>>` operators, which already mask their shift count to the low 5 bits for an `int` operand — exactly the `&0x1F` the SH-4 spec calls for, including the `Rm == Integer.MIN_VALUE` edge case (`-Rm` overflows back to `MIN_VALUE` in both Java and real 32-bit hardware, and `MIN_VALUE & 0x1F` is `0` either way).
  - `TAS.B @Rn` (test-and-set: read a byte, `T = (byte == 0)`, then unconditionally OR `0x80` into it and write it back) — real hardware does this as a single locked bus cycle for use as a mutex primitive; this interpreter runs single-threaded, so the plain read-then-write sequence is already equivalent.
  - All 6 opcodes cross-checked against multiple independent public sources (several different forks of QEMU's SH-4 disassembler tables, which agreed exactly) before implementation.
  - 9 new JUnit tests; 113 tests total in `core-cpu-sh4`.
- [x] **`core-cpu-sh4`: `STS.L`/`LDS.L` for `MACH`/`MACL`/`PR` — 6 new opcodes, found necessary by real game code, not by working down a spec checklist.**
  - Found via the real Sonic Adventure GD-ROM dump: after the boot-file-loading fixes above, `app-cli`'s SH-4 stepping loop executed 16 real instructions from the actual game before stopping on `Unimplemented SH-4 opcode 0x4F22` — which decodes to `STS.L PR,@-R15`, the classic SH-4 function-*prologue* instruction ("save my return address on the stack before I call anything else"). Its mirror image, `LDS.L @Rn+,PR` (the function-*epilogue* "restore it" instruction), plus the `MACH`/`MACL` forms of both (same instruction shape, different system register), were added alongside it rather than one at a time, since real code almost always needs the pair together.
  - All 6 opcode encodings (`0100nnnn0000/0001/0010 0010` for the `STS.L` pre-decrement-store family, `0100nnnn0000/0001/0010 0110` for the `LDS.L` post-increment-load family) confirmed against the same authoritative SH opcode table (binutils/QEMU's `sh-dis`/`sh4-dis` disassembler source, cross-referenced against multiple independent forks that agreed exactly) already used for the rotate/shift/`TAS.B` batch above.
  - 7 new JUnit tests, including a save-then-restore round trip through the stack for `PR` and — since this is the one real, confirmed case this project has actually observed a real disc need — a regression test using the literal opcode byte (`0x4F22`) and register (`R15`) the real Sonic Adventure dump hit, so this specific real-world finding can never silently regress. 120 tests total in `core-cpu-sh4`.
- [x] **`core-cpu-sh4`: `TRAPA`, plus `LDC Rn,VBR`/`STC VBR,Rn` — the project's "immediate recommended next step," followed proactively rather than waiting for a real disc to hit it.**
  - After `STS.L PR,@-R15` above was implemented, `app-cli` against the real Sonic Adventure dump ran the full 100,000-step budget with no unimplemented instruction hit — genuinely encouraging, but not a reason to stop: `TRAPA` was already the documented next step (it's the actual mechanism real HLE boot/syscall code uses to invoke BIOS-equivalent functionality — see /docs/ROADMAP.md), so it was implemented anyway rather than waiting for a real disc to eventually stumble on it.
  - `TRAPA #imm` performs the hardware-defined exception-entry sequence — `TRA = imm << 2`, `SSR = SR`, `SPC` = the return address, `PC = VBR + 0x100` — confirmed against the same authoritative SH opcode table (binutils/QEMU's `sh-dis`) used for every other opcode added this session. It does **not**, and cannot yet, do anything useful beyond that: this interpreter has no exception *handler* (no vector table, no BIOS to have installed one), so whatever's mapped at `VBR + 0x100` — nothing, unless the running code set up `VBR` itself first — determines what happens next, exactly like real hardware with no BIOS-installed handler.
  - Since `TRAPA` is meaningless without a `VBR` real code has actually set (real runtime-startup code always does this before relying on exceptions), `LDC Rn,VBR` and its mirror `STC VBR,Rn` were added alongside it — the first concrete pieces of the wider `LDC`/`STC` control-register family (see "Not started yet" below for the rest, still missing).
  - 4 new JUnit tests: the `TRAPA` entry sequence itself, `LDC`/`STC` each in isolation, and a realistic `LDC` → `TRAPA` sequence confirming a jump lands inside a just-set vector, not a stale one. 124 tests total in `core-cpu-sh4`.
- [x] **`core-gdrom`: `IpBinHeader` — parses a Dreamcast disc's IP.BIN boot header (hardware ID, product info, boot filename, game title). First concrete step of the BIOS-free HLE boot sequence.**
  - Reads the 256-byte descriptive header at the start of a disc's data track: hardware/maker ID, device info, area symbols, peripherals, product number/version, release date, and — most importantly for booting — the boot filename (typically `1ST_READ.BIN`) that a real BIOS would load and jump to.
  - **Field byte offsets validated 2026-07-26** against Marcus Comstedt's "Dreamcast Programming - IP0000.BIN" page (mc.pp.se/dc/ip0000.bin.html) — the original, most-cited authoritative public reference for this header, in continuous community use since 2000. Every field matches that reference exactly; no changes were needed to any offset. (The earlier cross-referenced reconstruction this replaces as the cited source turned out to have gotten every offset right anyway — but citing the single authoritative source directly is worth far more than that being true by luck.)
  - Also added, now that the Device Information field's documented sub-structure is known precisely: `calculateDeviceInfoCrc` (computes the CRC-16 a genuine disc's Device Info field should start with, over the raw Product Number + Product Version bytes) and `embeddedDeviceInfoCrc` (parses that 4-hex-digit CRC back out of a parsed header) — together, a way to sanity-check whether a disc image's header is internally consistent. The CRC algorithm itself (package-private `crc16Ccitt`) is verified against the standard, independently-published check value for the CRC-16/CCITT-FALSE variant it turns out to be (`0x29B1` for the ASCII string `"123456789"`), since no independently-sourced real Dreamcast product-number/version-to-CRC example was available to check the higher-level method against directly.
  - 9 JUnit tests total (5 original + 4 new for the CRC feature) against a hand-built synthetic header (fictional test data, not from any real game), covering field parsing, padding trimming, hardware-ID validation, a too-short-input error case, the CRC algorithm's standard check value, a full synthetic-header CRC round-trip, and a non-hex-digit CRC-prefix edge case.
- [x] **`core-gdrom`: `Iso9660FileSystem` — parses the ISO9660 Primary Volume Descriptor and root directory, enough to locate a Dreamcast boot file by name.**
  - `SectorSource` (a shared, narrow functional interface — `readSector(lba, dest)` — that `GdiImage`/`CueBinImage`/`CdiImage` all already match via method reference) and `LogicalSectorReader` (normalizes any track's raw sectors, 2352-byte or 2048-byte, into the plain 2048-byte logical sectors ISO9660/IP.BIN both need) factor out logic that was previously duplicated ad hoc in `app-cli`.
  - `Iso9660FileSystem.open(...)` validates and parses the Primary Volume Descriptor at the standard-mandated LBA 16, extracts its embedded root directory record, and can list or search that root directory. Deliberately scoped to the root directory only (no subdirectory recursion) since Dreamcast boot executables live there directly — a real, narrow capability rather than a half-finished general-purpose implementation.
  - `findInRootDirectory(name)` strips the ISO9660 `;1` version suffix from directory entries before matching, so it can be called directly with `IpBinHeader.bootFilename()`'s value. Resolves a file name to its extent (LBA + size).
  - **`readFile(record)` (new 2026-07-30):** reads a located file's actual bytes off disc, sector by sector via the same `SectorSource`/`LogicalSectorReader` normalization the rest of the class already uses, handling a partial final sector correctly. This is the piece that turns a resolved (LBA, size) pair into real, loadable bytes — see `HleBootLoader` below for what happens to them next.
  - **Bug found and fixed 2026-07-31, via the same real Sonic Adventure dump used for the track-selection fix above:** a Dreamcast GD-ROM high-density area's own ISO9660 directory records (root directory, every file) store `extentLba` using disc-*absolute* addressing (the high-density area always starts at physical LBA 45000 — confirmed against dreamcast.wiki's GDI format page and Redump's GD-ROM dumping documentation), not addressing relative to the extracted track. Reading those values directly (as the class did until now) looked for sectors ~45000 too far into the track and found nothing — this is what actually caused the "File not found" symptom the track-selection fix alone didn't resolve; the diagnostic listing confirmed the *right* track was finally open (`Root directory extent: LBA 45020, 40960 bytes`) but the entries list still came back empty. `Iso9660FileSystem.open` now detects this (a root directory `extentLba` at or past 45000 has no other plausible explanation) and transparently rebases every `extentLba` it reads by that amount; a plain single-session disc or the low-density area (small `extentLba` values) is unaffected.
  - `app-cli` now uses this to locate *and load* the boot file after printing the IP.BIN header, and was refactored to share `SectorSource`/`LogicalSectorReader` instead of its own duplicate extraction logic; also gained CDI support (previously GDI/CUE-BIN only) and a resource-leak fix (the opened disc image is now properly closed via try-with-resources).
  - 8 JUnit tests total (5 original + `readFile` across a multi-sector/partial-last-sector boot file with a distinctive non-zero byte pattern, so a wrong offset or truncated copy would fail loudly + a new one reproducing the exact high-density/disc-absolute-addressing layout that exposed the LBA rebase bug, confirming both the rebase itself and that the low-density/no-rebase path is unaffected) against hand-built synthetic ISO9660 volumes (fictional test data), covering PVD/root-directory parsing, directory listing (excluding "." and ".."), boot-file lookup with version-suffix stripping, a missing-file error case, rejection of an invalid PVD, full-file reading, and now high-density LBA rebasing. Verified end-to-end via `app-cli` and independent sandbox harnesses (see CHANGELOG) against both synthetic disc images and, for the track-selection half of this, real IP.BIN parsing from an actual Sonic Adventure GD-ROM dump.
- [x] **New `core-system` class `HleBootLoader` (2026-07-30): writes a boot file's bytes into a `SystemBus` at the real, documented Dreamcast boot address, and reports the SH-4 entry point.**
  - `BOOT_FILE_ENTRY_ADDRESS = 0x8C010000` — the SH-4 P1 (cache-enabled) virtual address real Dreamcast hardware loads the boot executable to and jumps to, confirmed against Marcus Comstedt's "Dreamcast Programming - IP.BIN and 1ST_READ.BIN" page (mc.pp.se/dc/ip.bin.html), the same authoritative source already used for `IpBinHeader`. Physically this lands at `MAIN_RAM_BASE + 0x10000` (right after the 0x8000-byte IP.BIN load area) once `SystemBus` masks off the P1 cache-select bits — verified by a test that writes through the physical address and reads back through the virtual one, and vice versa.
  - `loadBootFile(bus, bytes)` writes through the generic `Bus` interface (one byte at a time, no assumption about the target's internal representation — same design principle `Sh4Cpu` already follows) and returns the entry address as an `int`, ready to pass directly as `Sh4Cpu`'s initial PC.
  - Deliberately does not depend on `core-gdrom` or `core-cpu-sh4` — stays a narrow, generic "bytes in, entry address out" utility; the orchestration (reading the file, then constructing `Sh4Cpu` with the returned PC) lives in `app-cli`, which already depends on both.
  - **Known, documented limitation:** does not descramble CD-format (non-GD-ROM) `1ST_READ.BIN` files, which real CD masters store obfuscated as copy protection. Correct for GD-ROM-sourced dumps (this project's primary target); CD descrambling is a tracked follow-up, not silently wrong behavior — see "Not started yet" below.
  - 4 new JUnit tests covering the entry address constant, contiguous byte writes, and the physical/virtual address mapping both directions.
- [x] **`app-cli` now attempts an actual (if minimal) boot, not just inspection (2026-07-30).** After locating the boot file, it reads its bytes (`Iso9660FileSystem.readFile`), loads them into a real `SystemBus` at the documented address (`HleBootLoader`), constructs a real `Sh4Cpu` there, and steps it until either an unimplemented instruction stops it (expected, and reported with the exact PC and reason) or a 100,000-step budget is reached. This is the project's first end-to-end exercise of every piece built so far (IP.BIN parsing → ISO9660 lookup → disc reading → RAM loading → SH-4 execution) working together against one disc image — not a claim that any real game boots yet.
- [x] **New module `app-cli`: a simple command-line disc image inspector, usable while `app-javafx`'s GUI is still early.**
  - Detects a disc image's format, loads it (GDI, CUE/BIN, or CDI), locates its data track, reads the first sector, prints the parsed `IpBinHeader`, locates and reads the boot file it names, loads it into RAM, and steps the SH-4 from there (see the `HleBootLoader`/boot-attempt entries above).
  - Correctly handles both raw 2352-byte sectors (skipping the 16-byte sync/header preamble) and plain 2048-byte sectors, via the shared `LogicalSectorReader`.
  - **Bug found and fixed 2026-07-31, via a real disc image (Sonic Adventure), not synthetic test data:** GD-ROM images commonly have more than one data track — a small "single-density" area first (present purely so ordinary CD-ROM drives see *something* valid; it is not the game), then an audio track, then the real "high-density" game data as the LAST track. All three format openers (GDI, CUE/BIN, CDI) were picking the *first* data track, silently opening the wrong, nearly-empty filesystem (in the real disc image used to find this, that track's root directory held exactly 4 entries: the three standard ISO9660 placeholder files `ABSTRACT.TXT`/`BIBLIOGR.TXT`/`COPYRIGH.TXT` and an `EXTRA` directory — no boot file, because there wasn't one to find). Now they pick the *last* data track instead, the same convention real Dreamcast tools/emulators (redream, Flycast, etc.) already use. Diagnosed using a new `printRootDirectoryDiagnostics` fallback in `Main` that lists whatever the root directory actually contains when boot-file lookup fails, instead of just the bare error — kept in place for future debugging.
  - **Still does not run a real game to completion** — the interpreter only covers a subset of the SH-4 ISA (see "Not started yet"), so execution on real game code is expected to stop as soon as it needs `TRAPA`, the MMU, or real hardware register behavior. This tool reports exactly where and why it stopped; it is explicitly scoped as an inspection/smoke-test aid, not a game runner, and says so in its own output.
  - Run with: `./gradlew :app-cli:run --args="path/to/game.gdi"` (or `.cue`/`.cdi`). Verified end-to-end against hand-built synthetic disc images, *and*, as of 2026-07-31, a full confirmed real-world run against a real Sonic Adventure (USA) GD-ROM dump: IP.BIN parses correctly (hardware ID checksum `[OK]`, correct product number/title/etc.), `1ST_READ.BIN` is found (LBA 500703, 6,751,168 bytes) and loaded into RAM at `0x8C010000`, and the SH-4 executes real game instructions from it. **Confirmed twice now**: first for 16 real instructions before hitting `STS.L PR,@-R15` (fixed the same day — see the `TRAPA`/`STS.L`/`LDS.L` entries above); then, after that fix, for the **full 100,000-step budget with no unimplemented instruction hit at all** — since the old budget clearly wasn't a real ceiling, it was raised to 5,000,000 (also not yet independently re-confirmed against the real dump at the higher budget at time of writing).
- [x] **New module `common`, first real code in it: a small, dependency-free logging facility (`org.dreamjemu.common.log`) — requested 2026-07-31 by the project owner, implemented the same day.**

  - `Logger` (an SLF4J-style per-class facade — `Logger.get(SomeClass.class)`, kept in a `private static final` field), `LogLevel` (`TRACE`/`DEBUG`/`INFO`/`WARN`/`ERROR`/`OFF`), `LogRecord`, and `LogSink` (a pluggable output destination — defaults to `System.out`, swappable later for e.g. `app-javafx`'s planned debug console, with zero change needed in any module that just logs).   - Global level configurable via (in precedence order) `app-cli`'s new `--log-level LEVEL` flag, the `dreamjemu.log.level` system property, or the `DREAMJEMU_LOG_LEVEL` environment variable — falls back to `INFO` if none are set. - [x] **`app-cli`: new `LoopDetector` — detects a stable repeating PC cycle and stops stepping early with a summary, instead of silently exhausting the step budget (found necessary by real game code, same day as the logging module above).**
  - The real 5,000,000-step run above ran the *entire* budget with no unimplemented instruction hit — a `--log-level TRACE` run (redirected to a file; 5,000,054 lines) revealed why: a tight, stable 5-instruction loop — `MOV.B R4,@R5` / `ADD #1,R5` / `MOV.L @R6,R3` / `CMP/HS R3,R5` / `BF` back to the start — repeating identically millions of times. Almost certainly a legitimate `crt0`-style `.bss`-clearing loop (byte-at-a-time, hence slow), not a spin-wait on unmodeled hardware — but a multi-megabyte fill at one byte per five SH-4 instructions can trivially exceed any practical step budget, and there was no way to tell the two cases apart without detecting the repetition itself.
  - Algorithm: for each PC observed, remember the step index it was last seen at; when a PC recurs, the distance since its last occurrence is a candidate period; if that same period recurs a configurable number of times in a row (`app-cli` uses 1,000), the cycle is declared stable. Deliberately conservative (requires many *consecutive* identical-period repeats, not just one coincidental revisit) so a call/return pair or any other one-off address revisit can't misfire it.
  - On detection, `app-cli` prints the loop's period, how many repeats confirmed it, and the full loop body (every `PC`/`opcode` in one period, reconstructed from a small ring buffer kept alongside stepping) — then **continues stepping silently** (refined 2026-07-31, per the project owner, after a second real run found a second, earlier loop): loop detection is switched off after the first report (no further overhead, no repeated reports for the same or a later loop), and execution just keeps going until it hits something unimplemented or the step budget runs out. A single run can then show whether execution genuinely reaches new code afterward, not just that a loop exists.
  - Verified against a synthetic reproduction of the *exact* real loop (same 5 opcodes, a destination 1,000,000 bytes from its limit): detected in ~1,000 steps instead of exhausting a 5,000,000-step budget, with the confirmed period (5), repeat count (1,000), and genuine register-state progress (R5 actually advancing — this isn't a no-op) all checked. A further synthetic check confirms the "continue silently, don't re-report" behavior end-to-end: a detected loop that later genuinely exits into new code (here, one that then hits an intentionally-undefined opcode) is reported exactly once, with execution demonstrably continuing tens of thousands of steps past the report before reaching that new code.
  - **Confirmed 2026-07-31 on the project owner's own machine, against the real Sonic Adventure dump:** a *second*, earlier, faster (4-byte-at-a-time, `MOV.L`) fill loop at `PC=0x8C0100AE` was detected in 1,025 steps — different from the first (byte-at-a-time, `MOV.B`) loop found via the `--log-level TRACE` run that motivated this class in the first place, confirming real boot code does multiple sequential fills, not just one.
  - `LoopDetector` is deliberately small and self-contained — no knowledge of `Sh4Cpu`, `Bus`, or opcodes, just a PC-sequence utility — making it `app-cli`'s **first-ever unit-tested class**: everything else in the module is I/O-heavy CLI orchestration with no dedicated suite (see below), but this is genuinely pure, easily-testable logic. 8 new JUnit tests (non-repeating sequences never false-positive, the exact real loop shape detects correctly, threshold timing, only-fires-once semantics, interrupted periods don't silently accumulate, input validation, `reset()`, and a `repeatThreshold == 1` edge case that a first sandbox pass actually got wrong — see CHANGELOG).
